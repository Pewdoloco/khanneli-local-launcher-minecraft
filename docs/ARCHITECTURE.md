# Архитектура

## Стек
**.NET 8 / C#, WPF (UI позже) + консольное ядро на этапе 1.**

Почему:
- Нативный Windows, легко собирается в один exe (`PublishSingleFile`)
- Встроенный `System.Security.Cryptography` для SHA-256 — не нужна сторонняя либа для хеш-проверки
- Хорошо управляет процессами (`Process`, `StandardInput/Output`) — важно для обёртки над `.bat` и консолью сервера
- `HttpClient` + `Octokit` (опционально) для работы с GitHub Releases API
- Один язык/рантайм что для Client, что для Admin режима (Admin = Client + доп. модуль, а не отдельное приложение)

## Модули (этап 1 — Client)
```
VanillaLauncher.Client/
  Program.cs          — точка входа, консольный прогон
  ManifestModel.cs    — модель manifest.json
  ManifestService.cs  — скачивание manifest.json из GitHub Releases
  HashService.cs       — вычисление и сверка SHA-256
  UpdateService.cs     — сравнение локального состояния с манифестом, план докачки
  Downloader.cs        — докачка файлов по списку из плана
  AppConfig.cs          — пути, URL релиза, локальная папка сборки
```

## Формат manifest.json
```json
{
  "version": "26.1.2-b3",
  "generatedAt": "2026-07-12T00:00:00Z",
  "files": [
    {
      "path": "mods/sodium.jar",
      "sha256": "…",
      "size": 123456,
      "url": "https://github.com/YourOwner/YourModpackRepo/releases/download/1.0.0/sodium.jar"
    }
  ]
}
```
- `path` — относительный путь внутри клиентской папки профиля
- `sha256` — эталонный хеш файла
- `url` — прямая ссылка на GitHub Release asset (публичный репозиторий) либо
  на API-эндпоинт asset (приватный репозиторий + токен — отдельный этап)

## Поток обновления клиента (этап 1, без UI)
1. Скачать актуальный `manifest.json` из последнего релиза
2. Пройти по локальной папке сборки, посчитать SHA-256 существующих файлов
3. Сравнить с манифестом → получить список: новые / изменённые / без изменений
4. Скачать новые/изменённые файлы во временную папку → атомарно переместить на место
5. Логировать результат (что скачано, что пропущено)

## Модули (этап 2 — Client UI)
```
VanillaLauncher.Client.UI/
  App.xaml / App.xaml.cs
  MainWindow.xaml       — статус, кнопка "Проверить обновления", кнопка "Обновить", прогресс-бар, журнал
  MainWindow.xaml.cs    — код-behind: авто-проверка при запуске, докачка через существующие сервисы Client
  appsettings.json      — Link на src/VanillaLauncher.Client/appsettings.json (один источник конфига на оба exe)
```
UI не дублирует логику — ссылается на `VanillaLauncher.Client.csproj` и использует те же `AppConfig`, `ManifestService`, `UpdateService`, `Downloader`, `HashService`.

Для прогресс-бара `Downloader.ApplyAsync` в этапе 2 сменил `IProgress<string>` на структурный `IProgress<DownloadProgress>` (файл, completed/total, стадия Started/Completed) — по нему считается доля докачанных файлов. Байтовый прогресс внутри одного файла не считается (не требовалось спецификацией).

## Модули (этап 3 — Admin)
```
VanillaLauncher.Admin/
  ServerProcessController.cs   — обёртка над start.bat: старт через cmd.exe, построчный
                                  захват stdout/stderr, штатный stop через stdin

VanillaLauncher.Client.UI/
  AdminWindow.xaml(.cs)         — Старт/Стоп, лог консоли; открывается кнопкой
                                   "Режим администратора" из MainWindow
```
`ServerProcessController` — отдельная библиотека (не зависит от Client), Admin-окно ссылается
на неё напрямую, как MainWindow ссылается на Client.

Важный нюанс реализации: `cmd.exe /c` с **относительным** именем `.bat`-файла ненадёжно
резолвится в этом окружении (`dir`/`cd` подтверждают правильный working directory, .exe
запускаются нормально, но `.bat` — нет), поэтому `ServerProcessController` всегда передаёт
**абсолютный** путь к `.bat`.

Остановка: `stop` пишется в stdin процесса, затем stdin сразу закрывается (после этой команды
серверу ввод больше не нужен). Закрытый stdin — это то, что даёт финальному `pause` в `.bat`
завершиться сразу через EOF, а не зависнуть в ожидании интерактивного ввода. Никакого
принудительного `Kill` нет — только штатная остановка с таймаутом (по умолчанию используется
в UI 60 секунд); если сервер не уложился, это отражается в UI как предупреждение.

`ServerDirectory`/`ServerBatFileName` — новые поля `AppConfig`/`appsettings.json`, опциональные
(нужны только для Admin-режима, чисто клиентская сборка их не требует).

Авторизация Admin-режима на момент Этапа 3 ещё не была реализована — сделана отдельно в Этапе 6
(см. ниже).

## Модули (этап 4 — пересоздание мира)
```
VanillaLauncher.Admin/
  WorldBackupService.cs      — BackupWorld / RecreateWorld: архивация папки мира в zip
                                (backups/<levelName>_<таймстамп>.zip) + ротация по лимиту
  ServerPropertiesReader.cs  — level-name читается из server.properties, а не задаётся
                                отдельно в appsettings.json (одна точка правды)
```
`RecreateWorld` = обязательный `BackupWorld` (правило SPEC — без бэкапа не удаляем), затем
`Directory.Delete` папки мира; сервер сгенерирует новый мир на её месте при следующем запуске.
Метод синхронный — UI сам решает выносить ли вызов в `Task.Run`, чтобы не блокировать интерфейс
во время архивации.

`WorldBackupService` не проверяет, запущен ли сервер, — эта проверка на стороне UI
(`AdminWindow` отказывает, если `ServerProcessController.IsRunning`, и просит сначала
остановить сервер). Пересоздание мира на работающем сервере не поддерживается: оно бы
писало поверх данных, которые сервер ещё держит открытыми.

Ротация — по количеству файлов `<levelName>_*.zip` в `backups/`, самые старые (по времени
создания файла) удаляются сверх `MaxBackupsToKeep` (новое поле `AppConfig`, по умолчанию 5).

`AdminWindow`: кнопка "Пересоздать мир (с бэкапом)" — отказ, если сервер запущен;
иначе нативное подтверждение (`MessageBox`, Yes/No, дефолт No) с именем мира и явным
предупреждением, что мир будет удалён; после подтверждения — бэкап и удаление, путь к
бэкапу и результат пишутся в лог.

## Модули (этап 5 — публикация одной кнопкой)
```
VanillaLauncher.Client/
  ManifestGenerator.cs        — обход папки + хеширование, вынесено из tools/GenerateManifest
                                 (теперь используется и им, и Admin-пайплайном); URL строит
                                 вызывающая сторона через callback — генератор не знает,
                                 куда именно публикуется манифест

VanillaLauncher.Admin/
  GitHubReleaseClient.cs      — тонкий клиент GitHub REST API: создать релиз, загрузить ассет
  GitHubTokenProvider.cs      — токен только из переменной окружения VANILLALAUNCHER_GITHUB_TOKEN,
                                 нигде не хранится в репозитории/appsettings.json
  ReleasePublisher.cs         — генерирует манифест (ManifestGenerator) с плоскими GitHub-
                                 совместимыми URL и заливает его + все файлы в новый релиз
  ServerFileSync.cs           — зеркалирует mods/config из папки сборки в серверную папку
                                 (по хешу, с удалением устаревших файлов)
  PublishPipeline.cs          — оркестрация: бэкап мира -> стоп сервера -> синхронизация ->
                                 публикация манифеста (с engine-v1.6.0 сервер обратно НЕ
                                 запускается — см. раздел "Модули (этап — engine-v1.6.0...)")
```

**Плоские имена ассетов.** GitHub Release assets не поддерживают "/" в имени. `path` в
манифесте остаётся вложенным ("mods/sodium.jar" — так его ищет клиент локально), а имя
ассета на GitHub схлопывается (`ManifestGenerator.FlattenPathForAssetName`: "mods/sodium.jar"
→ "mods_sodium.jar"). `tools/GenerateManifest` получил флаг `--flat` для той же схемы при
ручной генерации; без флага (по умолчанию) сохраняется старое поведение с вложенным путём в
URL — годится для хостинга, который поддерживает папки, но не для реального GitHub Release.

**Каждый релиз самодостаточен.** Ассеты старых релизов не переиспользуются — каждая публикация
перезаливает все файлы заново. Осознанный компромисс: без этого манифест новой версии мог бы
ссылаться на ассет старого релиза, и его удаление (вручную, админом) сломало бы клиентам докачку
задним числом. Заливка ~200+ МБ модов на каждый релиз — цена этой надёжности.

**Пайплайн отказоустойчив только "вперёд".** Если любой шаг падает (не остановился сервер,
не удалось создать релиз, обвалилась сеть на середине аплоада), `PublishPipeline` не пытается
откатить уже сделанное и не запускает сервер обратно — состояние остаётся, где упало, чтобы
админ разобрался, а не чтобы код угадывал, как исправить частично опубликованный релиз.

**Токен.** Только через `VANILLALAUNCHER_GITHUB_TOKEN` — не файл, не appsettings.json, не
что-либо коммитящееся в репозиторий. Нужен PAT с правом `Contents: Read and write` на этот
репозиторий.

`AdminWindow`: поле ввода версии + кнопка "Опубликовать обновление" — подтверждение
(явно предупреждает, что релиз публичный), проверка токена/GitHubOwner/GitHubRepo до
запуска, лог прогресса по шагам пайплайна (было 5 шагов с автозапуском сервера в конце,
с engine-v1.6.0 — 4, без автозапуска).

**Проверено:** 26 xUnit-тестов (`GitHubReleaseClient`, `ReleasePublisher`, `ServerFileSync`,
`PublishPipeline`) — GitHub API замокан через `FakeHttpMessageHandler`, `PublishPipeline`
гоняется на синтетическом `.bat` (как в Этапе 3) от начала до конца, включая сценарий "сервер
не ответил на stop — пайплайн прерывается до синхронизации файлов".

**Живой прогон выполнен** (после подготовки к релизу) — и вскрыл реальную проблему,
см. следующий раздел.

## Живой прогон публикации и ServerExcludeMods

Первая настоящая публикация (`26.1.2-b1`) отработала пайплайн полностью — бэкап, синхронизация,
загрузка 171 файла в реальный GitHub Release, — но сервер после этого не запустился.

**Что произошло:** до синхронизации на `Server VS` было 122 мода — набор, который никогда не
совпадал 1:1 с клиентской папкой (`ProfileRoot`), это выяснилось только сейчас, потому что
раньше `ServerFileSync` ни разу не запускался на реальных данных. `MirrorAsync` зеркалирует
папку строго (лишнее в серверной папке удаляется) — значит после первого же реального прогона
все 45 модов, которых не было в клиенте, с сервера пропали, а сервер обзавёлся клиентскими
модами клиента, часть которых дедик-серверу не подходит. Один из них, `better_tab`
(`"environment": "*"` в fabric.mod.json — по метаданным универсальный), на деле в
main-entrypoint трогает `net.minecraft.client.gui.screens.Screen` и валит сервер на старте с
`NoClassDefFoundError`. Бэкапа старого набора модов сервера не оказалось — то, что было,
восстановить было неоткуда, договорились считать текущую клиентскую папку источником истины
и чинить дальше от неё (см. CHANGELOG.md).

**Решение — `ServerExcludeMods`** (новое поле `AppConfig`/`appsettings.json`, список имён
файлов): `ServerFileSync.MirrorAsync` принимает необязательный `excludeFileNames` и никогда
не копирует (и удаляет, если уже скопировано) файлы с такими именами на сервер — но именно
на сервер: манифест и клиентская раздача этот список не трогает, клиенты по-прежнему получают
все моды, включая клиентские (`sodium`, `iris` и т.д. — они нужны игрокам, просто не серверу).

Список составлен не на глаз: у каждого мода в `mods/` прочитан `fabric.mod.json` внутри jar
(это обычный zip), поле `environment`. 15 модов оказались явно `"client"`. `better_tab` не
поймать так — он единственный, кого добавили по факту реального краша (метаданные врут,
статический анализ таких случаев не ловит в принципе — это баг конкретного мода). Если в
будущем в модпак добавится новый клиентский мод, который сам не признаётся в этом честно,
единственный надёжный способ узнать — реально попробовать запустить сервер и посмотреть на
трассировку; поэтому это тоже описано в docs/ADMIN_GUIDE.md как процедура, а не только
финальный список.

**Итоговая проверка (всё настоящее, не смоделированное):**
- `Server VS` с 61 модом (77 клиентских минус 16 исключённых) стартовал: `Done (1.236s)! For
  help, type "help"`, без ошибок, штатно остановлен.
- Реальный клиент (свежий запуск, не тот же процесс, что публиковал) сверился с реальным
  манифестом `26.1.2-b1`: `Сборка актуальна`, `171 файл в манифесте`, `Расхождений не
  найдено` — то есть каждый локальный файл побайтово (по SHA-256) совпал с тем, что лежит на
  GitHub.
- 3 новых xUnit-теста на `ServerFileSync` с `excludeFileNames` (не копируется, удаляется, если
  уже было; регистронезависимо).

## Встроенный fallback для appsettings.json

Реальный пользователь скачал `VanillaLauncher.exe` из релиза по инструкции и получил крах:
файл `appsettings.json` в релиз не попал — при публикации `VanillaLauncher.exe` был залит
отдельным ассетом вручную (см. CHANGELOG.md), и про его соседа забыли. `AppConfig.Load()`
до этого момента считал отсутствие внешнего файла настройки фатальной ошибкой
(`FileNotFoundException`) — разумно для разработки, но означает, что судьба каждого релиза
зависит от того, не забыл ли кто-то приложить второй файл.

Исправлено на уровне кода, а не только "не забывать в следующий раз": `appsettings.json`
теперь ещё и `EmbeddedResource` в сборке `VanillaLauncher.Client`
(`LogicalName="VanillaLauncher.Client.appsettings.default.json"`) — тот же файл, что
копируется рядом с exe для локальной разработки, просто ещё и встроен в саму сборку.
`AppConfig.Load()`: если внешнего файла нет — читает встроенный дефолт вместо падения.
`_loadedFromDirectory` в обоих случаях выставляется на папку exe, так что `Save()`
(например, после выбора папки сборки на первом запуске — см. "Подготовка к релизу" ниже)
создаёт полноценный локальный файл вне зависимости от того, откуда был прочитан дефолт.

Проверено реальным сценарием: publish-сборка скопирована в пустую папку без единого
внешнего файла — запускается, работает, не падает. `VanillaLauncher.exe` в уже
опубликованном релизе `26.1.2-b1` заменён на пересобранный (с этим фиксом) через тот же
`GitHubReleaseClient` — старый ассет удалён, новый залит под тем же именем.

## Модули (этап 6 — авторизация Admin-режима)
```
VanillaLauncher.Admin/
  AdminAuthService.cs           — SetPassword/VerifyPassword/HasPassword: соль + PBKDF2-SHA256
                                   (100 000 итераций), сравнение хешей константным по времени

VanillaLauncher.Client.UI/
  SetAdminPasswordWindow.xaml(.cs)  — первый запуск: два поля (пароль + подтверждение)
  AdminLoginWindow.xaml(.cs)        — последующие запуски: одно поле, ошибка не закрывает окно
```
`MainWindow.AdminButton_Click` — гейт: если `AdminAuthService.HasPassword()` == false, показывает
`SetAdminPasswordWindow`; иначе `AdminLoginWindow`. `AdminWindow` создаётся только после
`ShowDialog() == true` — при отмене или неверном пароле не создаётся вообще.

**Файл с хешем.** `admin-auth.json` рядом с exe (там же, где `appsettings.json`) — то есть в
build output, который уже целиком в `.gitignore` (`bin/`); дополнительно сам файл тоже явно
внесён в `.gitignore` — если кто-то поменяет схему копирования файлов в output, хеш пароля всё
равно не закоммитится. Plaintext-пароль нигде не хранится и не логируется, только
соль (16 байт) + PBKDF2-хеш (32 байта, SHA-256, 100 000 итераций).

**"Привязка к ПК" не реализована.** SPEC.md отмечает её как опциональный пункт. Файл с хешем
и так физически лежит на конкретной машине — отдельный крипто-механизм (например, шифрование
через Windows DPAPI, которое бы намертво привязало файл к профилю Windows-пользователя) посчитали
избыточным для приватного сервера на несколько друзей: риск, который он закрывает (кто-то скопировал
`admin-auth.json` на другую машину и брутфорсит пароль оффлайн), не соответствует модели угроз
такого проекта.

**Проверено:** 8 xUnit-тестов на `AdminAuthService` (roundtrip верного/неверного пароля,
персистентность между инстансами, файл никогда не содержит plaintext, разные соли для
одинакового пароля). Сквозная проверка через живое UI Automation: первый запуск → установка
пароля → `AdminWindow` открывается; повторный запуск → неверный пароль отклоняется (диалог
не закрывается), верный пароль пускает.

## Подготовка к релизу (пост-Этап 6)

Три пробела всплыли, когда встал реальный вопрос "можно ли это скачать и запустить":

**1. ProfileRoot — папка конкретного человека, не константа.** Значение в `appsettings.json`,
которое уезжает внутрь exe при сборке, — это папка сборки автора. У любого другого человека,
скачавшего тот же exe, такой папки на диске не будет. Решение: `MainWindow` при старте
проверяет `Directory.Exists(ProfileRoot)`; если папки нет — показывает кнопку "Выбрать папку
сборки" (`Microsoft.Win32.OpenFolderDialog`, нативный, встроен в .NET 8 WPF), выбор
сохраняется через новый `AppConfig.Save()` обратно в **локальный** `appsettings.json` этого
человека. Ничего не коммитится — каждый друг правит только свою копию файла на своей машине.

**2. Необработанные исключения роняли всё приложение.** `AppConfig.Load()` бросает
исключение при отсутствии/поломке файла конфига — без обработки это крашило WPF-приложение
целиком со стектрейсом на экране. Для человека, которому просто прислали exe, это
неприемлемо. Исправлено: `MainWindow.InitializeAsync()` оборачивает загрузку конфига в
try/catch с понятным сообщением в статус-баре; `App.xaml.cs` дополнительно ловит
`DispatcherUnhandledException` глобально — любая необработанная ошибка показывается
`MessageBox`, а не роняет процесс.

**3. Не было ни publish-сборки, ни распространяемого exe.** До этого момента запускали
только через `dotnet run`/`dotnet build` (Debug). Настроена publish-сборка:

```powershell
cd src/VanillaLauncher.Client.UI
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true
```

`RuntimeIdentifier`/`SelfContained` сознательно **не** зашиты в основной `PropertyGroup`
csproj — если бы они были там безусловно, обычный `dotnet build`/`dotnet run` тоже стал бы
self-contained win-x64 сборкой: другой путь выхода (`bin/Debug/net8.0-windows/win-x64/`
вместо `.../net8.0-windows/`), что сломало бы все скрипты/тесты, завязанные на текущий путь,
и заметно замедлило бы каждую итерацию разработки. `IncludeNativeLibrariesForSelfExtract`/
`EnableCompressionInSingleFile` включены условно (`Condition="'$(PublishSingleFile)' == 'true'"`)
— применяются только во время публикации.

Результат — один exe (`VanillaLauncher.exe`, ~70 МБ, self-contained: другу не нужно ставить
.NET отдельно). Проверено запуском в полностью изолированной папке (без связи с dev-окружением)
с намеренно несуществующим `ProfileRoot` — онбординг (пункт 1) сработал корректно на реальной
publish-сборке, а не только в Debug.

## Модули (этап — настройка лаунчера под модпак)
```
VanillaLauncher.Client/
  PathAutoDetectService.cs   — TryFind(folderName, searchRoots): ищет прямую поддиректорию
                                с совпадающим (регистронезависимо) именем в каждом корне
                                поиска по порядку, не рекурсивно
  appsettings.default.json   — по-настоящему пустой embedded-шаблон движка (см. ниже)

VanillaLauncher.Client.UI/
  SettingsWindow.xaml(.cs)   — экран "Настройки": все Admin-поля из appsettings.json,
                                редактируемые; открывается только изнутри AdminWindow
```
См. docs/TASK_PATH_AUTODETECT.md — постановка задачи и Definition of Done.

**Модель "движок/модпак" — реализовано полностью.** Изначально (в рамках сессии, где
писался код автоопределения путей) репозиторий разделять на два не стали — сначала
сделали то, что относится к коду:
- Embedded-дефолт `AppConfig` (`appsettings.default.json`) по-настоящему пустой — без
  единого значения, специфичного для какого-либо конкретного модпака.
- `.github/workflows/engine-release.yml` — при пуше тега `engine-v*` собирает
  self-contained win-x64 exe и публикует его как GitHub Release этого репозитория,
  отдельно от релизов модпаков.

Позже репозиторий фактически разделили: этот репозиторий (`khanneli-local-launcher-minecraft`)
теперь и есть "движок" — только код, `appsettings.json` здесь тоже по-настоящему пустой (не
только embedded-дефолт). Контент/релизы конкретных модпаков живут в отдельных репозиториях,
не связанных с этим напрямую — из одного такого репозитория-примера в этот репозиторий
переехал весь код (`src/`, `tests/`, `tools/`, этот workflow) и доки о коде/архитектуре;
специфика самого модпака (`docs/SPEC.md`, `docs/ADMIN_GUIDE.md`, `docs/CLIENT_GUIDE.md`,
`docs/OVERVIEW.md`) осталась там. `CHANGELOG.md`/история ниже в этом файле — общая с тем
репозиторием до момента разделения; упоминания конкретного модпака в исторических разделах —
не конфигурация, а то, на каком реальном деплое движок разрабатывался и проверялся.

**`AppConfig.Load()` больше не бросает исключение на пустых `ManifestUrl`/`ProfileRoot`.**
Раньше отсутствие `ManifestUrl` в конфиге считалось ошибкой чтения файла
(`InvalidOperationException`). Но у "движка" без адаптации под модпак пустой конфиг —
это ожидаемое, валидное состояние, а не повреждённый файл. Вместо исключения — новое
свойство `AppConfig.IsConfigured` (`ManifestUrl`/`GitHubOwner`/`GitHubRepo` все заданы).
`ProfileRoot` в `IsConfigured` сознательно не участвует: это per-machine значение (у
каждого игрока — свой путь), которое легитимно пустое даже на полностью адаптированном
под модпак движке, пока конкретный игрок ещё не прошёл онбординг. `MainWindow` теперь
различает эти два случая явно: `!IsConfigured` → "лаунчер не настроен под модпак,
обратись к администратору" (кнопки проверки обновлений недоступны, `SelectProfileRootButton`
не показывается — выбирать путь смысла нет, если сам модпак не настроен); `IsConfigured`,
но `ProfileRoot` не существует на диске → обычный, ожидаемый онбординг конкретного игрока
(сначала автопоиск, потом ручной выбор).

**Автопоиск — `PathAutoDetectService.TryFind`.** Не рекурсивный, ищет только прямых потомков
переданных корней по точному (регистронезависимому) совпадению имени папки. Рекурсивный
обход всего диска сознательно не делали — непредсказуемо долго на больших дисках и находит
случайные совпадения имени в неожиданных местах.
- **Клиент:** корни поиска — `AppConfig.ClientSearchRoots` (список путей из конфига,
  например `D:\Games\curseforge\Instances`), имя — `ClientFolderName`. Ничего не
  подставляется автоматически, если оба поля пустые (типично для свежего, ещё не
  адаптированного под конкретную CurseForge-инсталляцию движка) — тогда сразу фоллбек на
  ручной выбор, как и раньше.
- **Сервер:** корни поиска — всегда папка рядом с `.exe` (`AppContext.BaseDirectory`, это
  и есть сценарий "создаётся рядом с лаунчером" из задачи) плюс опциональные
  `AppConfig.ServerSearchRoots` для нестандартных раскладок. Сценарий "инициализируется при
  старте лаунчера" отдельно не реализован как автоматическое создание папки — вместо этого
  ручной фоллбек использует `OpenFolderDialog`, который сам умеет создавать новую папку
  (кнопка "Создать папку" в диалоге), так что результат тот же без отдельного кода.
- Обе автодетект-точки (`MainWindow` для клиента, `AdminWindow` для сервера) при успехе сразу
  вызывают `AppConfig.Save()` — совпадение перепроверяется на каждом запуске (не кешируется
  отдельно), но раз найденный путь пишется в `appsettings.json`, так что при следующем
  запуске уже сам факт `Directory.Exists(ProfileRoot/ServerDirectory)` "срезает" повторный
  автопоиск, если ничего на диске не поменялось.

**Экран "Настройки" — `SettingsWindow`.** Не гейтится паролём отдельно — открывается только
кнопкой внутри уже открытого `AdminWindow` (`SettingsButton_Click`), то есть проход через
тот же `AdminAuthService`-гейт, что и весь Admin-режим, уже произошёл к этому моменту.
`MainWindow` про `SettingsWindow` вообще не знает — у обычного пользователя нет пути
достижения этого окна ни при каких обстоятельствах. Поля-списки (`ClientSearchRoots`,
`ServerSearchRoots`, `IncludeFolders`, `ServerExcludeMods`) редактируются как многострочный
текст, одна запись на строку — самый простой ввод, не требующий кастомного list-редактора
для полей, которые правятся раз в сто запусков. Кнопки "Найти автоматически" в этом окне
гоняют `PathAutoDetectService` по ещё не сохранённым значениям полей формы — позволяет
проверить имя/корни поиска до `Save()`, не перезапуская лаунчер.

## Модули (этап — env-переменные в путях, аудит модов из папки, встроенная инструкция)

Три доработки поверх этапа "настройка лаунчера под модпак" (запрошены после того, как
модель "движок/модпак" уже разошлась по отдельным репозиториям).

**Переменные окружения в `ClientSearchRoots`/`ServerSearchRoots`.**
`PathAutoDetectService.TryFind` перед проверкой каждого корня прогоняет его через
`Environment.ExpandEnvironmentVariables` (раскрывает `%USERPROFILE%`, `%LOCALAPPDATA%` и
любые другие Windows-переменные). Причина: `ClientSearchRoots` раньше приходилось задавать
абсолютным путём одного конкретного человека (`D:\Games\curseforge\Instances`) — не
работает у друзей с другим именем пользователя или диском. `%VAR%`, которого нет в
окружении, `ExpandEnvironmentVariables` не бросает исключение, а оставляет строку как
есть — она просто не найдётся на диске и тихо пропустится (как отсутствующий корень),
автопоиск перейдёт к следующему корню/фоллбеку. Найденный `TryFind` путь — уже
раскрытый конкретный путь этой машины, сохраняется в конфиг как обычно.

**Выбор модов из папки для `ServerExcludeMods` — `SelectExcludedModsWindow`.**
Раньше список редактировался только как текст (имя файла на строку) — нужно было точно
знать/переписывать имена jar вручную. Новое окно (открывается кнопкой в `SettingsWindow`,
по умолчанию подставляет `{ProfileRoot}\mods`) сканирует `*.jar` в выбранной папке
(`SearchOption.TopDirectoryOnly` — плоский список, как реальная папка модов) и показывает
чекбоксы, предварительно отмеченные по текущему `ServerExcludeMods`. Результат **не**
затирает список целиком: `SettingsWindow.PickExcludedMods_Click` мёржит отмеченные файлы
из просканированной папки с записями, которых в этой папке не было (например, введёнными
вручную для другого набора модов) — так пикер нельзя случайно использовать, чтобы стереть
не относящиеся к текущей папке исключения. Автоматизации самого решения "клиентский мод
или нет" здесь по-прежнему нет (см. "Что сознательно отложено") — это только замена
ручного набора текста на чекбоксы по реальному списку файлов.

**Встроенная инструкция — `GuideWindow` + `AppConfig.ClientGuide*`/`AdminGuide*`.**
Четыре новых строковых поля конфига (`ClientGuideShort`, `ClientGuideFull`,
`AdminGuideShort`, `AdminGuideFull`) с непустыми дефолтами из `DefaultGuides`
(`VanillaLauncher.Client`) — в отличие от путей/`ManifestUrl`, это осознанно не пустой
дефолт: сам по себе текст инструкции не содержит ничего специфичного для конкретного
модпака (описывает кнопки/поведение движка), поэтому он такой же generic-дефолт, как
`ServerBatFileName = "start.bat"` или `IncludeFolders = ["mods", "config"]` выше. Админ
переопределяет текст под свой модпак через `SettingsWindow` (четыре новых многострочных
поля внизу экрана), обычным `Save()`.

`GuideWindow` открывается кнопкой "Инструкция" в `MainWindow` (клиентский текст) и в
`AdminWindow` (админский) через `Show()`, не `ShowDialog()`, и без установки `Owner` в
смысле модальности (Owner проставлен только ради z-order/сворачивания вместе с
родительским окном) — специально, чтобы инструкцию можно было держать открытой и
одновременно продолжать пользоваться остальным лаунчером (например, сверяться с шагами
публикации, пока сама публикация идёт). Переключение "Краткое"/"Полное" — два `RadioButton`
на немедленную подмену текста в одном read-only `TextBox`; без прогонки текста markdown/HTML
разметки во что-то богаче, обычный текст (в кратком/полном формате) для этой задачи
достаточен.

*(Позже, `engine-v1.8.0`, добавился третий вариант длины — см. одноимённый раздел ниже.)*

## Модули (этап — самообновление exe движка)

Публикация модпака (Этап 5) никогда не трогает сам `VanillaLauncher.exe` — до этого этапа
единственным способом получить новую версию лаунчера было вручную получить файл от админа
(см. `docs/ADMIN_GUIDE.md` в репозитории модпака). Теперь exe умеет обновлять сам себя.

```
VanillaLauncher.Client/
  EngineVersion.cs        — const string Current, версия ЭТОЙ сборки движка
  EngineSelfUpdater.cs     — CheckForUpdateAsync (GitHub Releases API) +
                              PrepareAndLaunchUpdateAsync (скачать + подготовить рестарт)
```

**Откуда версия.** Не через `Assembly.GetName().Version`/`FileVersionInfo` — для
self-contained single-file публикации чтение версии сборки из рантайма ненадёжно
(`Assembly.Location` может быть пустым, single-file распаковывается во временную папку не
всегда предсказуемо). Вместо этого — обычная константа `EngineVersion.Current`, которую
правят руками вместе с пушем тега `engine-vX.Y.Z`. Хрупкое место (можно забыть
синхронизировать) закрыто на уровне CI: шаг `Verify EngineVersion.Current matches tag` в
`.github/workflows/engine-release.yml` вычитывает константу через `Select-String` и
проваливает публикацию, если она не совпадает с версией из тега — до того, как несовпадение
дойдёт до реальных пользователей.

**Проверка обновления — `EngineSelfUpdater.CheckForUpdateAsync`.** GET
`.../repos/{EngineGitHubOwner}/{EngineGitHubRepo}/releases/latest` (без токена — публичное
чтение). Тег, не начинающийся с `engine-v`, игнорируется (в репозитории движка других тегов
быть не должно, но код не полагается на это молча). Сравнение версий — `System.Version`
(не строковое), тег новее текущей — только тогда возвращается `Available`; если релиз новее,
но в нём нет ассета `VanillaLauncher.exe` (например, кто-то опубликовал релиз вручную без
файла или CI на середине), возвращается `UpToDate` — сообщать о "доступном" обновлении,
которое нечем накатить, хуже, чем промолчать.

**Применение — `EngineSelfUpdater.PrepareAndLaunchUpdateAsync`.** Windows не даёт переписать
байты уже запущенного exe (файл занят загруженным образом процесса), поэтому: скачанный exe
кладётся рядом как `VanillaLauncher.update.exe`, короткий сгенерированный `.bat` дожидается
завершения текущего процесса по PID (`tasklist`/`timeout` в цикле), затем `move` поверх
старого файла и `start` нового — сам `.bat` удаляет себя в конце. Метод **не** завершает
процесс сам — это специально оставлено вызывающей стороне (`MainWindow`,
`Application.Current.Shutdown()`), чтобы `EngineSelfUpdater` (проект `VanillaLauncher.Client`,
без ссылки на WPF) не зависел от `PresentationCore`. `appsettings.json`/`admin-auth.json`
рядом с exe не трогаются — обновляется только сам исполняемый файл.

**Конфиг — `EngineGitHubOwner`/`EngineGitHubRepo`.** Отдельные поля от `GitHubOwner`/
`GitHubRepo` (те — репозиторий модпака, куда публикуется контент). Реальный деплой обычно
указывает на этот самый репозиторий движка (`khanneli-local-launcher-minecraft`), но это два
концептуально разных репозитория даже при одном владельце — конфликтовать с моделью
"движок не знает про модпак" им не даёт то, что оба поля пустые по умолчанию и просто
отключают кнопку, если не заданы.

**UI — `MainWindow`.** Кнопка "Проверить обновление лаунчера" в клиентском (не Admin) окне
— осознанное решение: игроки чаще всего годами сидят на том exe, что им когда-то дал админ,
и раньше единственным способом получить свежую версию было получить файл от админа заново.
Самообновление снимает эту зависимость. `AdminWindow` его не дублирует — админ и так видит
`MainWindow` первым при каждом запуске. Применение подтверждается `MessageBox` (перезапуск
прерывает то, чем человек занимался) — в отличие от докачки модов, где подтверждение не
нужно, потому что она не закрывает приложение.

## Модули (этап — доработки экрана "Настройки" и окна "Инструкция" по обратной связи)

Пять точечных доработок после первого реального использования уже собранного функционала.

**`GuideWindow` — объединение ролей + защита от чужой модальности.** Раньше клиентская и
админская инструкция были двумя независимыми окнами; теперь одно окно с двумя переключателями
(роль: Пользователь/Администратор — крупным шрифтом, чтобы не перепутать; длина:
Краткое/Полное), см. `GuideRole`. Важнее: обнаружилось, что WPF `Window.ShowDialog()` по
умолчанию отключает **все** окна процесса, а не только своего `Owner` — так что любой модальный
диалог где угодно в приложении (`SettingsWindow`, `SelectExcludedModsWindow`,
`AdminLoginWindow`, `SetAdminPasswordWindow`) временно превращал открытую "Инструкцию" в
недоступную для взаимодействия, хотя по смыслу она должна оставаться читаемой всегда. Починено
перехватом `WM_ENABLE` в `GuideWindow.WndProc` (`HwndSource.AddHook`) — окно принудительно
возвращает себе enabled-состояние сразу после того, как WPF пытается его снять. Проверено
живьём: `IsWindowEnabled` у `GuideWindow` остаётся `True`, пока открыт модальный диалог пароля
администратора (у которого, ожидаемо, `IsWindowEnabled` = `False` — блокируется именно
владелец диалога, это штатно и не трогалось), и переключатель роли/длины внутри "Инструкции"
реально срабатывает в этот момент (не просто визуально "включено").

**Поля руководств в "Настройках" — read-only по умолчанию.** Четыре `TextBox` (`ClientGuideShort/Full`,
`AdminGuideShort/Full`) теперь `IsReadOnly="True"` пока не нажата кнопка "Редактировать" рядом
(`SettingsWindow.ToggleGuideEdit_Click`, ключ поля — `Tag` кнопки) — защита от случайного
ввода текста в это поле при правке соседних настроек. При входе в редактирование поле
одновременно увеличивается (`Height`: 80→320 для краткого, 140→380 для полного) для удобства
печати; кнопка меняет подпись на "Готово" и по повторному клику возвращает оба свойства
обратно. Само сохранение — по-прежнему только общей кнопкой "Сохранить" внизу окна.

**`ClientSearchRoots` — непустой generic-дефолт.** Раньше пустой список по умолчанию означал,
что автопоиск клиентской папки в принципе не мог сработать, пока админ не впишет хотя бы один
корень поиска руками. Теперь дефолт — `%USERPROFILE%\curseforge\Instances` (везде: C#-инициализатор
свойства, `appsettings.default.json`, loose `appsettings.json`) — это стандартный путь
установки CurseForge-приложения, не относится ни к какому конкретному модпаку (тот же
принцип, что у `ServerBatFileName = "start.bat"`), и `PathAutoDetectService` раскрывает
`%USERPROFILE%` в реальный путь на машине каждого игрока независимо от имени пользователя.

**Постоянная кнопка "Сменить папку сборки" в `MainWindow`.** Раньше кнопка выбора
`ProfileRoot` появлялась только в сценарии "путь не найден" (`Visibility.Collapsed` в
остальное время) — у игрока не было способа поменять путь самостоятельно, если он один раз
уже был выбран корректно, но, например, сборку переустановили в другое место. Кнопка теперь
видна и активна всегда; `SelectProfileRootButton_Click` подхватывает `_config` через
`??= AppConfig.Load()` (на случай клика до завершения `InitializeAsync`) и перезапускает
проверку обновлений только если `_config.IsConfigured`.

**`SelectExcludedModsWindow` — поиск и постраничный вывод.** Модпаки легко содержат 70-100+
модов — сплошной прокручиваемый список неудобно просматривать и невозможно быстро найти
конкретный файл. Список теперь по `PageSize = 10` строк за раз (кнопки "◀ Пред."/"След. ▶",
подпись "Страница X из Y (N файлов)", в духе списка игр в библиотеке Steam) + поиск по
подстроке имени файла (`TextBox` + кнопка "Найти", тоже по Enter). Отмеченное состояние
хранится в `HashSet<string> _checkedNames`, не зависящем от того, что отрисовано на текущей
странице/фильтре — иначе переключение страницы или повторный поиск сбрасывали бы чекбоксы вне
видимой части списка. При "Применить" `SelectedExcludedMods` считается пересечением
`_checkedNames` с `_allJarNames` (полный список из скана, не только текущий фильтр) — так
поиск сам по себе никогда не теряет отметки, сделанные до него.

**Более явные подписи `GitHubOwner`/`GitHubRepo` vs `EngineGitHubOwner`/`EngineGitHubRepo`.**
Обе пары формально одинаковы (Owner — имя пользователя/организации на GitHub, Repo — имя
репозитория внутри него), но указывают на два разных репозитория (модпак-контент vs код
движка) — в `SettingsWindow.xaml` это было неочевидно из одних только имён полей. Добавлены
явные заголовки разделов ("Репозиторий МОДПАКА" / "Репозиторий ДВИЖКА") и поясняющий текст
серым под каждым. Заодно у `ManifestUrl` и `ServerExcludeMods` появились аналогичные
пояснения (что это, откуда брать, как соотносится с кнопкой-пикером рядом).

**Фикс валидации `MaxBackupsToKeep`.** `WorldBackupService` (см. Этап 4) всегда требовал
`>= 1` (бросает `ArgumentOutOfRangeException` иначе), но `SettingsWindow` до этого момента
разрешал сохранить `0` — несостыковка, которая проявилась бы только в момент реального клика
"Пересоздать мир" в `AdminWindow`, необязательно сразу после сохранения настроек. Граница
проверки в `SaveButton_Click` приведена в соответствие (`< 1`, было `< 0`).

## Модули (этап — `engine-v1.3.0`, живой прогон публикации на реальном модпаке)

Первая настоящая живая публикация на реальном модпаке после разделения движок/модпак
(предыдущий живой прогон, "Живой прогон публикации и ServerExcludeMods" выше, был ещё в
едином репозитории). Полная сводка — CHANGELOG.md, тот же заголовок. Здесь — детали по
новым классам.

**`GitHubRepoNameNormalizer`** (`VanillaLauncher.Client`) — статический метод `Normalize`,
вызывается из `SettingsWindow.SaveButton_Click` для полей `GitHubRepo`/`EngineGitHubRepo`.
Причина: `GitHubReleaseClient`/`EngineSelfUpdater` строят URL из голого имени репозитория
(`api.github.com/repos/{owner}/{repo}/...`), а поле легко перепутать со ссылкой на сам
репозиторий (оно так и называется — "репозиторий"). Вырезает схему/хост/`.git`-суффикс,
если распознаёт URL или `owner/repo` формат; если это уже голое имя — не трогает.

**`GitHubApiErrorTranslator`** (`VanillaLauncher.Client`) — `TryGetHint(HttpStatusCode, string
responseBody)`, возвращает человекочитаемую подсказку для частых ошибок GitHub API (404 —
неверный репозиторий, 403 "Resource not accessible" — токену не хватает прав, 422
"Repository is empty" — в репозитории модпака нет коммитов, 422 "already exists" — версия
уже опубликована) или `null` для нераспознанных случаев. Подключён и в
`GitHubReleaseClient.EnsureSuccessAsync` (публикация), и в `EngineSelfUpdater.CheckForUpdateAsync`
(самообновление) — подсказка добавляется отдельной строкой поверх сырого сообщения GitHub,
само сырое сообщение не убирается (нужно для отладки нераспознанных случаев).

**`GitHubReleaseClient.UploadAssetAsync` теперь возвращает `browser_download_url`.** GitHub
переименовывает ассеты релиза при сохранении (например, заменяет пробелы на точки в имени
файла) — ссылка, посчитанная заранее из исходного имени (как было раньше), не всегда совпадала
с реальной. `ReleasePublisher.PublishAsync` теперь берёт `entry.Url` из возврата
`UploadAssetAsync` уже ПОСЛЕ загрузки каждого файла, а не предсказывает его до. Манифест
по-прежнему строится сразу (для расчёта хешей), но URL в нём перезаписывается настоящим.

**`FabricModEnvironmentReader`** (`VanillaLauncher.Client`) — читает `fabric.mod.json` внутри
`.jar` (это обычный zip) через `System.IO.Compression.ZipFile`, возвращает значение поля
`"environment"` или `null` (нет файла/поля/битый zip — везде `null`, не исключение).
`SelectExcludedModsWindow.ScanFolder` использует его, чтобы предотметить чекбоксы модов с
`"environment": "client"` и подписать их `[авто: environment=client]` — экономит админу время
на честно объявленных модах, но не отменяет ручную проверку (см. "Что сознательно отложено").

**`SelectExcludedModsWindow` — фикс отображения имён с "_".** `CheckBox.Content` рендерится
через `AccessText`, где одиночный `_` — маркер мнемоники (как в "_File" → подчёркнутая "F") —
пропадал из отображаемого текста, хотя реальные данные (какой файл реально отмечен) были не
затронуты (используется имя из замыкания, не разбор Content). Фикс — экранирование `_` → `__`
только в отображаемом тексте.

**`MainWindow`/`AdminWindow` `LogList` — перенос длинных строк.** Раньше — одна строка на
элемент списка без переноса, длинные сообщения (особенно JSON-ошибки GitHub) уезжали за
пределы окна с горизонтальной прокруткой. Добавлен `ItemTemplate` с `TextWrapping="Wrap"`,
`ScrollViewer.HorizontalScrollBarVisibility="Disabled"`.

**`GuideWindow` — разделение по ролям.** Раньше обе роли (Пользователь/Администратор) были
видны из любого окна намеренно (см. исходный комментарий в XAML, теперь удалён) — решение
пересмотрено по фидбеку: из `MainWindow` (клиент) `AdminRoleRadio` скрывается в конструкторе
(`Visibility.Collapsed`), из `AdminWindow` доступны обе.

## Модули (этап — `engine-v1.3.1`/`engine-v1.4.0`, самовосстановление конфига и самонастройка клиента)

**`AppConfig.Load()` — appsettings.json теперь появляется на диске сам.** Раньше при
отсутствующем внешнем файле `Load()` брал встроенный `appsettings.default.json` только для
работы в памяти, никогда не писал его обратно на диск — "удали appsettings.json и
перезапусти" из `ClientGuide` не работало (файл так и не появлялся, лаунчер каждый раз

файла не было — `try/catch` на `IOException`/`UnauthorizedAccessException`, чтобы не уронить
запуск в папке без прав на запись (та же причина, ради которой вообще есть этот фоллбек).
Существующий файл `Load()` не трогает.

**`ClientSetupWindow` — самостоятельная настройка клиента без Admin-режима.** До этой версии
единственный способ раздать игрокам рабочий exe — заранее настроенная пара exe+

сразу обычная проверка обновлений. GitHubRepo нормализуется тем же `GitHubRepoNameNormalizer`,

"Настройки" (пароль, ServerDirectory, публикация) не изменились, только Admin-режим.

**`EngineRepositoryDefaults`** — константы `Owner = "Pewdoloco"`, `Repo =
"khanneli-local-launcher-minecraft"`, используются как фоллбек в `MainWindow.
CheckEngineUpdateButton_Click`, когда `EngineGitHubOwner`/`EngineGitHubRepo` в конфиге пустые.
Раньше пустые поля просто отключали кнопку "Проверить обновление лаунчера" с сообщением "не
задано в Настройках" — теперь самообновление работает из коробки для любого модпака на этом

своим движком) фоллбек не перезаписывает и не игнорирует — применяется только когда поле
пустое.

## Модули (этап — `engine-v1.6.0`, ручной контроль сервера, вотермарка версии)

По фидбоду после `engine-v1.5.0`: админ хотел явно контролировать, когда сервер запущен, а
не обнаруживать постфактум, что пайплайн публикации его перезапустил или что окно закрылось,
оставив сервер висеть в фоне без явного подтверждения.

**`PublishPipeline` больше не запускает сервер после публикации.** Шаг "5/5: запуск сервера"
убран — пайплайн теперь 4 шага (бэкап → стоп → синхронизация → манифест), заканчивается с
сервером остановленным независимо от того, был ли он запущен до публикации. Админ нажимает
"Запустить сервер" сам, когда готов — это даёт возможность сначала проверить консоль на
`NoClassDefFoundError`/`Failed to start` (см. раздел про client-only моды выше), прежде чем
пускать игроков. `PublishPipelineTests` обновлены — обе смок-проверки ("сервер уже остановлен"
и "сервер был запущен") теперь ассертят `Assert.False(controller.IsRunning)` после `RunAsync`.

**`AdminWindow` — явное подтверждение остановки сервера.**
- `StopButton_Click` — при успешной штатной остановке теперь показывает
  `MessageBox` ("Сервер остановлен.") — раньше единственная обратная связь была пассивным
  обновлением `StatusText` через обработчик `ServerProcessController.Exited`, легко пропустить,
  если не смотреть на окно именно в этот момент.
- `Window_Closing` — раньше просто предупреждал, что сервер продолжит работать в фоне, но не
  мешал закрыться. Теперь, если сервер запущен, закрытие **отменяется** (`e.Cancel = true`) и
  вместо этого предлагается диалог "Остановить сервер и закрыть?" — при "Да" пайплайн реально
  дожидается `StopAsync`, показывает подтверждение и только потом закрывает окно
  программно (`_closingAfterServerStopped` — флаг, чтобы повторный `Closing` не поймал
  собственное же закрытие в цикл диалогов).

**Вотермарка последней опубликованной версии в поле "Версия релиза".** `AdminWindow`
асинхронно (best-effort, без токена) запрашивает `GET /repos/{owner}/{repo}/releases/latest`
при открытии окна и, если GitHubOwner/GitHubRepo заданы и релиз существует, показывает тег
серым текстом внутри пустого поля (`было: {tag}`) через `VisualBrush`, обновляемый в
code-behind (не статический XAML-триггер, как для `EngineGitHubOwner`/`Repo` — значение
динамическое, известно только после сетевого запроса). Переключается туда-обратно по
`TextChanged`: набранный текст скрывает вотермарку, очистка поля возвращает её обратно.

## Модули (этап — `engine-v1.9.0`, локализация RU/EN и минималистичный визуальный стиль)

По запросу пользователя: тумблер языка интерфейса (RU/EN) + минималистичный дизайн
(Windows 11/macOS-подобный). Полная сводка — `CHANGELOG.md`, тот же заголовок.

**Локализация — `VanillaLauncher.Client.UI.Localization` (`Strings.cs` + `Loc.cs`).**
`Strings` — статический `Dictionary<string, (string Ru, string En)>`, ключ на каждую строку
chrome-интерфейса (заголовки, кнопки, подписи, watermark, статус/лог, диалоги, ошибки) во всех
8 окнах + `App.xaml.cs`. `Loc` — синглтон с `INotifyPropertyChanged`, XAML использует
индексаторный биндинг `{Binding Source={x:Static loc:Loc.Instance}, Path=[Key]}`; смена
`Loc.Instance.Language` поднимает `PropertyChanged` с `Binding.IndexerName` — WPF перечитывает
разом ЛЮБОЙ индексаторный биндинг во ВСЕХ уже открытых окнах, без перезапуска приложения и без
ручного кода обновления на каждое окно. `AppConfig.Language` (`"ru"`/`"en"`, дефолт `"ru"`)
персистится в `appsettings.json`, читается в `App.OnStartup` до создания `MainWindow` (чтобы не
мигать дефолтным языком долю секунды). Тумблер РУС/ENG — пара кнопок в `MainWindow`/
`AdminWindow`.

**Не переведено осознанно: текст `DefaultGuides`/`AppConfig.ClientGuide*`/`AdminGuide*`.** Это
admin-авторский контент конкретного модпака (как `ServerExcludeMods` — данные, а не UI chrome);
переводить чужой текст автоматически не входит в задачу. Локализован только сам `GuideWindow`
(заголовок окна, переключатели роли/длины) — тело инструкции остаётся на языке, на котором его
написал админ.

**Статус/лог — не всегда живое обновление, и это осознанно.** Прямое присваивание
`TextBlock.Text` в code-behind (а не биндинг) технически снимает XAML-биндинг с этого
`DependencyProperty` — вот почему переключение языка само по себе не обновляет уже показанный
статус. Для большинства статусов это не проблема (следующее действие пользователя
перегенерирует текст на новом языке). Два самых заметных исключения — `MainWindow.StatusText`/
`EngineStatusText` и `AdminWindow.StatusText` — получили `SetStatus`/`SetEngineStatus`
(запоминают последний ключ+аргументы в `_statusKey`/`_statusArgs`, `SetLanguage` их
перерисовывает) — иначе первое, что видит пользователь сразу после переключения языка, могло
быть смесью языков. Кнопки нативного `MessageBox` (Да/Нет/ОК/Отмена) остаются на языке ОС
Windows — системная область, недоступная для переопределения без замены на кастомные окна
(осознанно не делали).

**Баг, найденный и исправленный при разработке: `Run.Text` и `BindsTwoWayByDefault`.**
`SettingsWindow` падала с `XamlParseException` при открытии — `System.Windows.Documents.Run`
регистрирует `Text` с `FrameworkPropertyMetadataOptions.BindsTwoWayByDefault` (в отличие от
`TextBlock.Text`/`Button.Content`, которые по умолчанию `OneWay`), а `Loc.this[string]` —
индексатор только для чтения; WPF не может создать `TwoWay`-биндинг на read-only индексатор.
Оба `<Run>` (вступительный абзац `SettingsWindow`) получили явный `Mode=OneWay`. Единственное
место в проекте, где встречается `<Run>` — везде остальной текст через `TextBlock.Text`/
`Button.Content`, у которых эта проблема не воспроизводится.

**Минималистичный стиль — `Styles.xaml`.** Общий `ResourceDictionary`, подключён один раз в
`App.xaml` (`Application.Resources.MergedDictionaries`) — applies каскадно implicit-стилями
(`Style TargetType="..."` без `x:Key`) ко всем окнам, ни одно окно не подключает стиль отдельно.
Светлая нейтральная палитра (`#F5F5F7` фон / `#1D1D1F` текст / акцент `#2563EB`), плоские кнопки
со скруглёнными углами через кастомный `ControlTemplate` (`Border` + `ContentPresenter`,
hover/pressed/disabled — через `Trigger`, не системный `ButtonChrome`), скруглённые
`TextBox`/`PasswordBox` с акцентной рамкой в фокусе, `ListBox`/`ListBoxItem` с плоским
hover/selected. `AccentButton` — отдельный именованный стиль (не implicit) для кнопки главного
действия экрана (`Опубликовать обновление`, `Сохранить`, `Войти`, `Задать пароль`,
`Применить`) — явно применяется только на этих кнопках, не перекрашивает вообще все кнопки
подряд. Системный chrome окна (заголовок/рамка/кнопки свернуть-закрыть) сознательно не
трогали — кастомный `WindowChrome`/`AllowsTransparency` ломает штатное перетаскивание/resize,

## Модули (этап — `engine-v1.10.0`, интерактивная консоль сервера + фикс кодировки cmd.exe)

По запросу пользователя: возможность отправлять произвольные команды серверу из консоли
Admin-режима, плюс баг-репорт "нечитаемая абракадабра при остановке сервера".

**`ServerProcessController.SendCommandAsync(command)`** — пишет строку в stdin процесса без
закрытия потока (в отличие от `StopAsync`, где закрытие stdin после "stop" осознанно нужно,
чтобы завершить висящий `pause` в конце `.bat`). `AdminWindow` — новое поле
`CommandInputTextBox` + кнопка "Отправить"/`Admin.SendCommandButton`, `Enter` в поле тоже
отправляет. `IsEnabled` выставляется везде, где меняется `StopButton.IsEnabled` (через новый
хелпер `SetCommandInputEnabled`) — сервер должен быть запущен и стабилен (не во время
старта/остановки/публикации). Введённая команда логируется отдельной строкой с префиксом
`> ` перед фактической отправкой — консоль сервера эту команду сама не печатает, только
ответ на неё.

**Фикс кодировки вывода `cmd.exe`.** `cmd.exe` пишет собственные сообщения (в т.ч. приглашение
`pause` при закрытии stdin) в OEM-кодпейдже консоли (866 для ru-RU), не в ANSI/UTF-8; без
явного `StandardOutputEncoding` в `ProcessStartInfo` .NET декодирует их наугад — абракадабра
вместо `Для продолжения нажмите любую клавишу . . .`. Исправлено: `StandardOutputEncoding`/
`StandardErrorEncoding`/`StandardInputEncoding` теперь = `Encoding.GetEncoding(GetOEMCP())`.

Источник кодпейджа — **прямой P/Invoke `GetOEMCP()` из `kernel32.dll`**, не
`CultureInfo.CurrentCulture.TextInfo.OEMCodePage` — первая версия фикса использовала именно
`CultureInfo`, и вживую воспроизвела баг СНОВА, просто с другим набором мусорных символов: на
машине с системной локалью ru-RU (`chcp` подтверждает 866) `CultureInfo.CurrentCulture`
внутри процесса неожиданно резолвился в `en-AI` (English — Anguilla), что дало
`OEMCodePage = 850`. `CultureInfo.CurrentCulture` — ненадёжный источник для этой задачи (может
быть переопределён множеством способов, необязательно совпадает с реальной консольной
кодировкой ОС); `GetOEMCP()` — тот же самый WinAPI-вызов, которым пользуется сам
`cmd.exe`/`chcp`, поэтому единственный по-настоящему надёжный источник.
`System.Text.Encoding.CodePages` (NuGet) + `Encoding.RegisterProvider(CodePagesEncodingProvider.
Instance)` в статическом конструкторе — .NET Core/5+ не регистрирует OEM/ANSI кодпейджи по
умолчанию, только Unicode-семейство.

Смешанность неизбежна: сам Java-процесс сервера обычно пишет в UTF-8 и не подчиняется этой
кодировке, но подавляющее большинство строк лога сервера (ASCII) от выбора кодпейджа не
зависит — страдали только сообщения самого `cmd.exe`, они теперь читаются корректно.

Текст встроенной "Инструкции" (`AdminShort`/`AdminFull`, RU и EN) обновлён — новое поле
ввода команд упомянуто в разделе кнопок Admin-режима.

123 теста (было 121) — 2 новых на синтетическом `.bat`-харнесе (`SendCommandAsync_
WritesToStdin_WithoutStoppingServer`, `SendCommandAsync_ServerNotRunning_Throws`), тот же
принцип, что и у остальных тестов `ServerProcessController` (настоящий Minecraft-сервер не
поднимается). Живой прогон: реальный UI, запуск фейкового сервера, отправка команды через
новое поле (эхо в лог + ответ сервера подтверждены на экране), остановка — сообщение `pause`
показывает корректный читаемый русский текст.

## Модули (этап — `engine-v1.12.0`, смоук-тест сервера перед публикацией)

Реакция на реальный инцидент: клиентский мод просочился в серверную сборку (соврал в
метаданных про `environment`, или его забыли добавить в `ServerExcludeMods`) и уронил старт
сервера — обнаружилось это только постфактум, вручную, уже после того, как обновление

**`ServerSmokeTestRunner.cs` (VanillaLauncher.Admin).** Короткий тестовый запуск сервера:
подписывается на `OutputReceived`/`Exited` того же `ServerProcessController`, что использует
`AdminWindow`, вызывает `Start()` и ждёт первого из трёх исходов через
`TaskCompletionSource`/`Task.WhenAny` с таймаутом: строка готовности `Done (...)!`
(`ServerLogLineClassifier.IsSuccessLine`) — `Success`; `Exited` раньше неё — `Crashed`; ничего
из этого за отведённое время — `TimedOut`. При `Success` сервер штатно останавливается
(`StopAsync`, тот же таймаут, что и у остальных шагов пайплайна); при `Crashed`/`TimedOut`,
если процесс всё ещё жив (актуально только для `TimedOut` — при `Crashed` он уже сам вышел),
вызывается новый `ServerProcessController.Kill()` (`Process.Kill(entireProcessTree: true)`) —
никакого штатного "stop" зависшему/упавшему процессу слать бессмысленно. Результат —
`ServerSmokeTestResult` с исходом и полным выводом за время теста, плюс `ErrorLines` (фильтр
через `ServerLogLineClassifier.IsErrorLine`) для короткого сообщения администратору вместо
всего лога.

**`ServerLogLineClassifier.cs` (VanillaLauncher.Admin).** `IsSuccessLine`/`IsErrorLine` —
вынесены из приватной code-behind логики `AdminWindow` (жили там с `engine-v1.10.0`/`v1.10.1`,
непереиспользуемые за пределами окна и непокрытые тестами напрямую) в общий тестируемый класс.
`AdminWindow` теперь тоже вызывает его (индикатор `StartOutcomeText`, панель "Ошибки") — не
дублирует логику, риска разъехаться с `ServerSmokeTestRunner` больше нет.

**`PublishPipeline` — новый шаг 4/5.** Между синхронизацией серверных файлов (`ServerFileSync`)
и генерацией/публикацией манифеста (`ReleasePublisher`) добавлен вызов
`ServerSmokeTestRunner.RunAsync` на том же `serverController`, что передан в пайплайн. Если
исход не `Success` — пайплайн бросает `InvalidOperationException` с описанием причины и
похожими на ошибку строками вывода, `ReleasePublisher.PublishAsync` не вызывается вообще:
на GitHub ничего не уходит. Синхронизированные файлы сервера при этом остаются как есть —
пайплайн, как и раньше (см. класс-комментарий), не пытается откатывать состояние при отказе
какого-либо шага, только останавливается на месте. Новый необязательный параметр
`smokeTestTimeout` (по умолчанию 120 секунд) — отдельный от `stopTimeout`, так как ждать
готовности сервера обычно дольше, чем ждать его штатной остановки.

**Фикс гонки в `AdminWindow.EnsureController()`.** Смоук-тест запускает/останавливает сервер
через тот же `ServerProcessController`, чьи `OutputReceived`/`Exited` уже подписаны на
UI-логику `AdminWindow` (обновление лога, индикатор старта, счётчик игроков, кнопки). Без
защиты общий обработчик `Exited` перетирал бы `StatusText` с "Публикация «X»..." на "Сервер

## Модули (этап — `engine-v1.13.0`, определение виновного jar при смоук-тесте, файловое логирование)

статический метод, ищет .jar-файлы с ZIP-записью, у которой общий флаг "есть data descriptor"
(бит 3) выставлен, а метод сжатия — STORED, а не DEFLATED. По спецификации ZIP этот флаг
допустим только для DEFLATED-записей; `java.util.zip.ZipInputStream` (его использует
`securejarhandler` Forge/NeoForge при сканировании `mods`) на этом строго падает с
`ZipException: only DEFLATED entries can have EXT descriptor` — мгновенно, ДО того как
успевает залогировать, какой файл виноват (ровно так и произошло на `Dwarfs` — три клиентских
мода: `oculus`, `smoothswapping`, `sodiumextras`). Сам jar при этом не обязательно повреждён —
так его просто собрал сборщик мода; для строгого Java-ридера это тем не менее фатально.
Разбирает только Central Directory (в конце файла) по офсетам из спецификации ZIP — не
распаковывает содержимое, быстро и не грузит весь jar в память. `PublishPipeline` вызывает его
для `serverDirectory/mods` при любом провале смоук-теста и подставляет список файлов-кандидатов
в сообщение об ошибке — надёжная (не эвристика, точный побитовый разбор), но узкая проверка:
ловит именно этот класс краша, не все возможные причины падения сервера.

**`FileLogger.cs` (VanillaLauncher.Client).** Один файл на запуск процесса
(`logs/launcher-{yyyyMMdd-HHmmss}.log`, рядом с exe), `StreamWriter` с `AutoFlush = true` —
построчно, без буферизации, чтобы последняя строка перед крашем не терялась. Чистка старых
файлов — ПОСЛЕ создания текущего (тот же порядок, что у `WorldBackupService.RotateBackups`):
скан `logs/` видит уже и новый файл, `Skip(MaxFilesToKeep)` по `CreationTimeUtc` держит на диске
ровно `MaxFilesToKeep` (20) файлов включая текущий, а не 21. Best-effort по конструкции — если
папка недоступна для записи, `FilePath` остаётся `null`, `Log()` просто ничего не делает,
никогда не роняя и не блокируя основную работу приложения (тот же принцип, что у
`AppConfig.Save()`).

Один экземпляр на весь процесс — `App.Logger` (публичное статическое поле, `App.xaml.cs`,
инициализируется до конструктора `MainWindow`, так как `StartupUri` создаёт его сразу после
`OnStartup`). `MainWindow.Log()`/`AdminWindow.Log()` пишут в него с префиксом `[Client]`/
`[Admin]` — единая хронология событий обоих окон в одном файле, а не два разрозненных. (Только
`Log()`, не `LogError()` — та лишь дублирует те же строки в отдельную UI-панель "Ошибки", без
файлового вызова строка не потерялась бы дважды.) `App.OnDispatcherUnhandledException` пишет в
файл полный `e.Exception.ToString()` (стектрейс + вложенные `InnerException`) ДО показа
дружелюбного `MessageBox` игроку — раньше эта информация терялась безвозвратно сразу после
закрытия диалога. `App.OnExit` вызывает `Logger.Dispose()`.

## Модули (этап — `engine-v1.14.0`, Forge называет виновный мод, фикс обрезания текста в консоли)

Прямое продолжение `engine-v1.13.0` — по итогам живого прогона на реальном инциденте (`Dwarfs`,
второй мод подряд после трёх предыдущих) пользователь дал фидбек по скриншотам: одна конкретная

**`ForgeModStateTableParser.cs` (VanillaLauncher.Admin).** `FindFailedModJars(lines)` — разбирает
строки на `|`-разделённые колонки, первая колонка должна заканчиваться на `.jar`, любая из
остальных колонок (после `Trim()`) должна точно равняться `ERROR` (без учёта регистра). Формат —
стандартный отчёт Forge/NeoForge о загрузке модов (`ИмяФайла.jar |Имя |modid |версия |СТАТУС
|доп. инфо`), печатается сервером при провале инициализации мода. Надёжнее и универсальнее
`JarDataDescriptorScanner` (`v1.13.0`) — не привязан к одному конкретному классу краша — но
появляется в выводе позже, только если сервер дошёл до стадии загрузки модов (пережил
первичное сканирование папки `mods`, на котором как раз падает ZIP-дефект из `v1.13.0`). Поэтому
в `PublishPipeline` обе проверки идут по очереди, не взаимоисключающе: сначала
`ForgeModStateTableParser` (по всему `smokeTest.Output`, не только `ErrorLines` — хотя эта
конкретная строка и так попадает в `ErrorLines`, так как содержит подстроку `"ERROR"`), затем
`JarDataDescriptorScanner` — обе заметки добавляются в сообщение об ошибке, если найдены обе.
Найденному виновнику сразу сопровождается готовая инструкция — добавить имя файла в
`ServerExcludeMods` (экран "Настройки") и убрать сам jar из папки `mods` на сервере.

**Фикс обрезания текста в консоли.** `LogList`/`ErrorLogList` в `AdminWindow.xaml` и `LogList` в
`MainWindow.xaml` — добавлен `VirtualizingPanel.ScrollUnit="Item"`. Причина бага: элементы этих
`ListBox` — `TextBlock` с `TextWrapping="Wrap"`, то есть переменной высоты (зависит от длины
строки лога); WPF по умолчанию скроллит виртуализированные списки с переменной высотой элементов
попиксельно (`ScrollUnit="Pixel"`), из-за чего элемент у границы видимой области мог оказаться
обрезан по вертикали ровно посередине текста. `ScrollUnit="Item"` переключает на поэлементную
прокрутку — элемент показывается либо целиком, либо не показывается вовсе, обрезания нет.

Живой прогон (PowerShell UI Automation на реальном exe, синтетический `.bat` с настоящей

**`ServerLogLineClassifier.IsErrorLine` — точная классификация вместо голого `Contains`.**

пропускала в панель "Ошибки" обычные WARN-строки Log4j, если их СООБЩЕНИЕ просто упоминало
исключение — например `[main/WARN] [mixin/]: Error loading class: ... (java.lang.RuntimeException:
...)` (реальная строка из живого прогона `v1.14.0`/`v1.15.0`) — предупреждение, не ошибка, но
"RuntimeException" внутри текста проходил старый фильтр. Пользователь явно попросил: только
реальные ошибки, предупреждения не нужны. Новая логика требует один из явных маркеров:
Log4j-формат уровня (`[поток/ERROR]`/`[поток/FATAL]`, в квадратных скобках), таблица

`ForgeModStateTableParser`, но здесь — более дешёвая проверка без парсинга остальных колонок:
просто split по `|` и точное совпадение обрезанного сегмента со словом `ERROR`), либо raw-строки
крашдампа JVM без префикса уровня (`Exception in thread ...`, `at ...`, `Caused by:`,
`Suppressed:`). Использует ту же функцию `AdminWindow` (панель "Ошибки") и
`ServerSmokeTestRunner`/`PublishPipeline` (`ErrorLines` в сообщении об ошибке публикации) — все
существующие синтетические `.bat`-фикстуры тестов (`[ERROR]:`, `Exception in thread`, таблица
Forge) продолжают матчиться под новой логикой без изменений.

Прямое продолжение `engine-v1.18.0`. Пользователь спросил про полноценное редактирование
whitelist/ops/`server.properties` из лаунчера (структурированный экран настроек), после оценки
объёма заменил на компактную вещь — адрес сервера с копированием (`v1.18.0`). Затем уточнил
важную деталь своего реального деплоя: `server-ip` в `server.properties` обычно уже содержит
Tailscale IP (сервер намеренно слушает только на этом интерфейсе — так игроки вне Tailscale-сети
физически не могут даже увидеть сервер), и это поле часто настроено ДО того, как админ вообще
открывает лаунчер — раньше значение приходилось вручную дублировать в `AppConfig.ServerHost`.

**`ServerPropertiesReader` — новые `GetServerIp`/`GetServerPort`/`SetServerAddress`.**
`GetServerIp`/`GetServerPort` — точечное чтение по ключу; заодно `GetLevelName` рефакторен на тот
же общий приватный `GetValue(serverDirectory, key)` вместо дублирования построчного сканирования
(до этого их читал только `GetLevelName`, теперь общий метод переиспользуется тремя читателями).
`GetServerIp` возвращает `null`, если ключ пуст или отсутствует — пустой `server-ip` в ванильном
Minecraft означает "слушать на всех интерфейсах", это НЕ то же самое, что "не настроено" для
целей UI, но и не значение, которое стоит подставлять как адрес для игроков. `SetServerAddress`
точечно правит `server-ip`/`server-port` в существующих строках файла (порядок, комментарии,
остальные ключи не трогаются) либо дописывает ключ в конец, если его ещё нет.

**`AdminWindow` — поля адреса сервера стали редактируемыми.** `ServerHostInlineTextBox`/
`ServerPortInlineTextBox` заменили статичный `TextBlock` из `v1.18.0`. Сознательно НЕ полноценный
live two-way биндинг между `server.properties` и `AppConfig` — потребовал бы слежки за внешними
правками файла (`FileSystemWatcher`) и обработки конфликтов при расхождении, признано избыточным
для этой задачи. Вместо этого простой паттерн:
- **Чтение (`RefreshServerAddressFields`)** — приоритет у `server.properties` (если папка
  сервера известна и там заполнено непустое значение — это то, чем реально пользуется
  запущенный сервер), фоллбек на `AppConfig.ServerHost`/`ServerPort`. Вызывается при открытии
  окна, после выбора папки сервера вручную и после сохранения "Настроек" — НЕ при переключении
  языка (сами значения адреса от языка не зависят, перерисовывается только соседняя
  локализованная подпись/подсказка через обычный XAML-биндинг, без кода).
- **Запись (`SaveServerAddressButton_Click`)** — при нажатии "Сохранить" пишет и в
  `AppConfig`/`appsettings.json` (используется проверкой доступности в `MainWindow`,
  `ServerReachabilityChecker`, `v1.11.0`), и в `server.properties` через `SetServerAddress`
  (если папка сервера известна) — оба места остаются синхронными от момента правки, без
  необходимости лезть в оба места вручную. Валидация порта (1–65535) переиспользует тот же
  ключ локализации ошибки, что и `SettingsWindow` (`Settings.ServerPortError`).
- Подсказка под полями прямым текстом предупреждает: правка вступает в силу только после
  следующего перезапуска сервера — Minecraft читает `server.properties` только при старте
  процесса, "живой" правки на лету не бывает ни у одного форка.

**Обзор архитектуры на дублирование/мёртвый код (по запросу пользователя).** Проверка `Strings.cs`
нашла и удалила два неиспользуемых ключа: `Admin.ServerStopped.MessageBox` (остаток модалки,
убранной в `v1.10.1` — сосед `Admin.PublishDone.MessageBox` был корректно удалён в `v1.16.0`, этот
пропустили) и `Common.AppTitle` (не читается — `MainWindow` собирает заголовок окна напрямую
строковой интерполяцией). Отдельно найдено, но осознанно НЕ тронуто по решению пользователя —
несколько мест копипасты между `MainWindow`/`AdminWindow` (методы вида `SetStatus`/аналоги,
тумблер языка, `Log()`, XAML-шаблон `ListBox`-строк) — чисто стилистическая уборка без
функционального риска, отложена.

Живой прогон (PowerShell UI Automation): поля при открытии показывают значение из
`server.properties` (не устаревшее значение из `appsettings.json`, специально проверено на

## Модули (этап — `engine-v1.20.0`, фикс классификатора ошибок, синхронизация с сервером без публикации)

Прямое продолжение диагностики живого инцидента на `Dwarfs` из предыдущей сессии (см.
`docs/HANDOFF.md`) — краш от `apoli` (библиотеки внутри `Origins`) начинался со строки
`java.util.concurrent.ExecutionException: java.lang.AbstractMethodError: ...`, которую панель
"Ошибки" не ловила: ни `[ERROR]`/`[FATAL]`, ни `Exception in thread` в начале строки не было.
Пользователь подтвердил оба предложенных тогда, но не сделанных фикса.

**`ServerLogLineClassifier.IsErrorLine` — маркер заголовка необёрнутого исключения.** Новый
`WrappedExceptionHeader` (`Regex`, `^[\w.$]*(Exception|Error)(:|$)`) ловит строки, которые САМИ
являются именем класса Java-исключения — например `java.util.concurrent.ExecutionException: ...`
или `java.lang.NoClassDefFoundError: ...` без обёртки `Exception in thread`/уровня Log4j. Якорь
на начало строки (после `Trim`) — принципиально не ловит упоминание исключения ВНУТРИ чужого
сообщения (тот WARN-кейс из `v1.16.0`, `[main/WARN] ...: Error loading class: ... (RuntimeException:
...)`, по-прежнему игнорируется — регекс не матчит строку, начинающуюся с `[`).

**`PublishPipeline` — общий `SyncAndSmokeTestAsync`.** Первые 4 шага `RunAsync` (бэкап мира ->
остановка сервера -> синхронизация серверных файлов -> смоук-тест) вынесены в приватный
`SyncAndSmokeTestAsync(..., totalSteps)` — параметр `totalSteps` только для текста прогресса
("Шаг N/4" при синхронизации, "Шаг N/5" при публикации, где шаг 5 — сама публикация манифеста).
Логика ошибки смоук-теста (виновный jar от `ForgeModStateTableParser`/`JarDataDescriptorScanner`,
похожие на ошибку строки) осталась общей, но текст сообщения обезличен от GitHub-специфики
("Синхронизированные файлы сервера остались как есть" вместо прежнего "на GitHub ничего не
загружено") — теперь одинаково уместен в обоих контекстах. Новый публичный `SyncOnlyAsync`
вызывает тот же приватный метод с `totalSteps: 4` и без шага публикации.

**`AdminWindow` — кнопка "Синхронизировать с сервером (без публикации)".** До этого фикса
единственным способом проверить, не сломает ли смена модов на клиенте сервер, была либо реальная
публикация (риск потратить время на смоук-тест ради самой проверки, нужен GitHub-токен), либо
ручная правка файлов на сервере в обход лаунчера — именно так админ временно чинил `Dwarfs` в
предыдущей сессии. Новая кнопка (рядом с "Пересоздать мир") вызывает `SyncOnlyAsync` напрямую —
без токена, без подтверждающего диалога, без загрузки манифеста/релиза. Переиспользует
существующий флаг "публикация идёт" (`PublishButton.IsEnabled`) как признак "публикация ИЛИ
синхронизация идёт" — обе кнопки теперь выключают/включают друг друга и себя синхронно, поэтому
защита от гонки с `Exited`-обработчиком контроллера сервера (см. `EnsureController`, введена в
`v1.12.0` для смоук-теста публикации) автоматически покрывает и новую кнопку без отдельного кода.

**Проверено:** 95 тестов в `VanillaLauncher.Admin.Tests` (было 93, +2 — реальная строка
`ExecutionException` из инцидента и голый `NoClassDefFoundError` в `ServerLogLineClassifierTests`).
Живой прогон (PowerShell UI Automation, синтетический `.bat` вместо реального Minecraft-сервера):
кнопка отрисовывается корректно рядом с "Пересоздать мир" без визуальных регрессий; успешный
прогон синхронизирует моды в серверную папку и создаёт бэкап мира без единого обращения к
GitHub; отдельный прогон с `.bat`, эмулирующим реальную строку краша `ExecutionException` —
панель "Ошибки" показывает её (раньше пропускала), статус и `MessageBox` корректно сообщают об
ошибке без каких-либо действий с GitHub.

## Модули (этап — `engine-v1.21.0`, тёмная тема, карточки в AdminWindow, иерархия кнопок)

По запросу пользователя ("работа над внешним видом лаунчера, минимальный стиль оставляем") —
уточнены приоритеты через явный выбор (визуальная группировка/отступы/тёмная тема/иерархия
текста-кнопок — выбраны все четыре, начать с `AdminWindow`).

**Тёмная тема (`ThemeManager.cs`, новый класс, `VanillaLauncher.Client.UI`).** Цветовые токены,
раньше жившие прямо в `Styles.xaml` (`AccentBrush`, `SurfaceBrush`, `TextBrush` и т.д.), вынесены
в `Theme.Light.xaml`/`Theme.Dark.xaml` — два словаря с одинаковыми ключами, разными значениями.
`Styles.xaml` больше не определяет цвета, только структуру/шаблоны контролов, и ссылается на
цветовые ключи через `DynamicResource` (было `StaticResource` — принципиальная замена, без неё
подмена словаря не обновила бы уже открытые окна). `App.xaml` мержит `Theme.Light.xaml` первым
(дефолт до первого вызова `ThemeManager.Apply`) и `Styles.xaml` вторым.
`ThemeManager.Apply(theme)` находит текущую тему-запись в `Application.Resources.MergedDictionaries`
по имени файла-источника и заменяет её словарём другой темы. Один найденный по ходу нюанс:
**`Window.Background`, заданный через implicit-стиль (`TargetType="Window"`), не перекрашивался
сам по себе** при такой подмене — дочерние элементы (кнопки, `ListBox`) переоценивали
`DynamicResource` штатно через визуальное дерево, а вот корневой фон окна оставался от прежней
темы. `InvalidateVisual`/`UpdateLayout` не помогли — рабочим фиксом оказался явный
`window.SetResourceReference(Window.BackgroundProperty, "WindowBackgroundBrush")` на каждом
открытом окне (`Application.Current.Windows`) внутри `ThemeManager.Apply` — создаёт живую ссылку
на уровне конкретного инстанса, а не только через `Style`.

Тумблер ☀/☾ — тот же `LanguageToggleButton`/`LanguageToggleContainer`, что у РУС/ENG (рядом в
обоих окнах), просто с другим набором кнопок и `ThemeLightButton_Click`/`ThemeDarkButton_Click` в
code-behind. `AppConfig.Theme` (новое поле, `"light"`/`"dark"`, дефолт `"light"`) — тот же паттерн
персистентности, что `Language`. Применяется до показа стартового окна в `App.OnStartup` (вместе
с языком, из того же `AppConfig.Load()`), чтобы не мигать светлой темой на долю секунды при
запуске в тёмной — см. аналогичный комментарий про язык там же.

Заодно у `ComboBox` (используется в памятке команд `AdminWindow`) не было своего стиля — тянул
хардкодный белый фон WPF по умолчанию, в тёмной теме выглядел бы белым пятном. Добавлен полный
`ControlTemplate` (`ToggleButton` + `Popup` + `ItemsPresenter`) в стиле остальных контролов.

Все инлайновые `{StaticResource ...Brush}` в остальных окнах (`MainWindow`, `SettingsWindow`,
`SelectExcludedModsWindow`, `ClientSetupWindow`, `GuideWindow`, `AdminLoginWindow`,
`SetAdminPasswordWindow`) заменены на `DynamicResource` — механическая замена (только
`MutedTextBrush` в большинстве файлов), но без неё эти окна не подхватили бы переключение темы у
уже открытого экземпляра (при повторном открытии с нуля `StaticResource` резолвился бы верно и
так, проблема только с live-переключением).

**Карточки в `AdminWindow` (новый стиль `Card`, `Styles.xaml`).** Контролы перегруппированы в
шесть визуальных секций — "Сервер" (адрес, игроки, старт/стоп/настройки/инструкция), "Мир и
синхронизация" (пересоздание мира, `SyncOnlyButton` из `v1.20.0`), "Публикация" (версия +

**Иерархия кнопок (новый стиль `GhostButton`, `Styles.xaml`).** Прозрачный фон в состоянии покоя,

## Модули (этап — `engine-v1.22.0`, фикс темы для новых окон, карточки в Инструкции/Настройках)

По итогам живого прогона `engine-v1.21.0` пользователь прислал скриншоты `GuideWindow`/
`SettingsWindow`, открытых поверх уже тёмного `AdminWindow` — оба оставались светлыми, плюс
сообщил про обрезание нижней рамки консоли/ошибок при уменьшении окна.

**Тема для новых окон — корневая причина глубже, чем казалось в `v1.21.0`.** Точечный
`SetResourceReference` внутри `ThemeManager.Apply` (см. запись `engine-v1.21.0` выше) исправлял
только окна, которые уже существовали в момент переключения (перебирал
`Application.Current.Windows`) — но `GuideWindow`/`SettingsWindow` открываются ПОСЛЕ, кнопками
из уже открытого `AdminWindow`, и на момент их создания implicit-стиль `Window` с
`DynamicResource` для `Background` почему-то тоже не резолвился в актуальную тему (не только
проблема "живого" переключения у уже открытых окон, как предполагалось раньше). Настоящий фикс —
централизованный, в `App.OnStartup`:
```
EventManager.RegisterClassHandler(typeof(Window), Window.LoadedEvent, (sender, _) =>
    ((Window)sender).SetResourceReference(Window.BackgroundProperty, "WindowBackgroundBrush"));
```
Один обработчик на `Window.Loaded` для ЛЮБОГО окна приложения — срабатывает при создании КАЖДОГО
окна (включая будущие, ещё не написанные), а не только для окон, живущих на момент вызова
`ThemeManager.Apply`. Точечный цикл в `ThemeManager.Apply` по `Application.Current.Windows`
оставлен — он всё ещё нужен для другого сценария (live-переключение темы у уже ОТКРЫТОГО окна,
`Window.Loaded` для него уже не сработает повторно).

**Обрезание рамок — недооценённый `MinHeight`.** `AdminWindow` из `v1.21.0` получил
`MinHeight="700"`, но реальный минимум для карточек с новыми отступами (шесть карточек, паддинг
16px + `SectionHeading`-отступы) — заметно больше. `Border` по умолчанию не клипует содержимое —
когда пользователь ужимал окно ниже фактически нужной высоты, `ListBox` с заданным `MinHeight`
(140/90 из `v1.21.0`) продолжал требовать своё место и протекал за нижний скруглённый край
карточки, из-за чего казалось, что рамка просто пропала. Два независимых фикса: `MinHeight`
поднят до 920 (равен дефолтной `Height` — окно физически невозможно сжать до состояния, где
контент не помещается), и `ClipToBounds="True"` добавлен в стиль `Card` — если где-то ещё
всплывёт похожий случай переполнения, контент обрежется по краю карточки, а не вылезет наружу.

**Карточки в `GuideWindow`.** Всё содержимое (переключатель роли, переключатель длины, текст
инструкции) — теперь внутри одной карточки `Card`, а не голым `Grid` на фоне окна. Заодно убран

чинилось в других окнах в `v1.21.0`, просто пропущенный случай.

**Карточки в `SettingsWindow`.** Разбит на пять смысловых карточек — "Клиент" (`ProfileRoot` +
автопоиск), "Сервер" (`ServerDirectory` + автопоиск + `ServerBatFileName`), "Подключение"
(`ServerHost`/`ServerPort`), "Публикация модпака" (`ManifestUrl`, репозитории модпака/движка,
`IncludeFolders`, `ServerExcludeMods`, `MaxBackupsToKeep`), "Инструкции" (все шесть текстовых
редакторов гайдов). Раньше это был один длинный `StackPanel` внутри `ScrollViewer` без визуальной
группировки — саму структуру полей и порядок не трогали, только обернули в `Card` с заголовками
(`SectionHeading`, новые ключи локализации `Settings.*CardHeader`).

попросил добавить материал про Tailscale и типовые ошибки администратора — оба раздела написаны

инструкций", о которой сообщил пользователь. Контент — обобщение реальных инцидентов из этой и
прошлых сессий (не привязан к конкретному модпаку, см. общий принцип файла в шапке класса):
- **Настройка Tailscale** — что это, как подключить сервер и игроков к одной сети, где взять
  IP/MagicDNS-имя, куда его вписать (поле «Адрес сервера» = `server-ip` в `server.properties`),
  и важный нюанс из реальной диагностики этой сессии — подключаться через `localhost`, если
  играешь с той же машины, что и сервер (иначе лишний пинг через VPN-туннель к себе же).
- **Частые ошибки администратора** — «Сервер недоступен» (Tailscale в первую очередь),
  `session.lock`/файл занят при бэкапе (обычно разовая гонка, повтори), панель «Ошибки» ловит
  не каждый краш (`ServerLogLineClassifier.IsErrorLine` — набор конкретных маркеров, не
  гарантия; смотри полную консоль), диагностика TPS через `spark tps`/`spark health` прямо в
  консоли команд, низкий FPS у игроков — не серверная проблема, обычно радиус LOD-прорисовки
  Distant Horizons.

**Проверено:** 186 тестов без изменений (WPF-разметка/стили + текстовые константы, вне зоны
покрытия юнит-тестов). Живой прогон (PowerShell UI Automation, скриншоты, тема выставлена в
`appsettings.json` до старта, чтобы сразу открыться тёмной): `GuideWindow`/`SettingsWindow`,
открытые из уже тёмного `AdminWindow`, теперь тоже тёмные (до фикса были светлыми несмотря на
тёмный `AdminWindow` рядом); карточки в обоих окнах — читаемый контраст, найдены по актуальным
`x:Name`/заголовкам через дерево UI Automation (окна открываются с `Owner`, поэтому лежат в
дереве как дети `AdminWindow`, не root — см. существующий раздел про этот нюанс UI Automation
ниже в этом файле).

**Скроллбары и приглушённый текст тёмной темы — вторая правка по тому же живому прогону.**
Пользователь прислал ещё один скриншот `SettingsWindow` и указал на два визуальных недочёта:
резкий почти-белый текст ("выжигает глаза") и явно светлые полосы, похожие на рамки, справа от
скроллящихся областей. `Styles.xaml` до этой правки вообще не переопределял `ScrollBar` — контрол
рисовался системным (светлым, Windows Aero-подобным) шаблоном независимо от активной темы
приложения, поэтому на тёмном фоне выглядел яркой белой полосой (это и были "белые рамки" из
фидбека, не рамки полей ввода). Добавлен `Style TargetType="ScrollBar"` — плоский минималистичный
скроллбар без стрелок-кнопок (`RepeatButton` с `Opacity="0"` вместо скрытия — так `Track`
по-прежнему получает клики по "странице" мимо бегунка), только `Thumb` со скруглением, цвет из
новых токенов `ScrollBarThumbBrush`/`ScrollBarThumbHoverBrush` (добавлены в оба `Theme.*.xaml`).
Отдельным фиксом `TextColor` тёмной темы смягчён с `#F2F2F3` (95% яркости) до `#DADADC` — тот же
принцип "off-white", что у большинства тёмных UI (VS Code, GitHub Dark), контраста для чтения
достаточно, но без ощущения "режет глаза" на весь экран текста.

**Проверено:** живой прогон (PowerShell UI Automation, скриншоты `SettingsWindow`/`AdminWindow`
в тёмной теме, тот же тестовый рецепт, что выше) подтвердил — бегунок скроллбара теперь тёмный,
почти сливается с фоном карточки вне hover, текст читается мягче на прежнем месте.

## Что сознательно отложено
- Переиспользование ассетов между релизами (см. выше, почему не делали)
- Привязка Admin-пароля к конкретному ПК (см. выше, почему не делали)
- Проверка целостности скачанного exe при самообновлении (SHA-256/подпись) — TLS обеспечивает
  подлинность канала загрузки с GitHub, отдельной сверки хеша (как у манифеста модпака) нет;
  сознательный компромисс ради простоты первой версии функции
- Цифровая подпись exe (SmartScreen может ругаться на первый запуск — см. docs/CLIENT_GUIDE.md)
- Частичная автоматизация аудита `ServerExcludeMods` — **сделана частично** в `engine-v1.3.0`
  (`FabricModEnvironmentReader` + автоотметка в `SelectExcludedModsWindow`, см. соответствующий
  раздел ниже): ловит честные `"environment": "client"`, но не ловит моды, которые лгут в
  метаданных (`"*"`, но на деле клиентские, например `better_tab`) — для них по-прежнему нужен
  реальный запуск сервера и разбор лога, полностью автоматизировать это не выйдет в принципе
  (см. `docs/ADMIN_GUIDE.md` в репозитории модпака)
