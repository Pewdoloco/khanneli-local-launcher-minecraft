## ОТКРЫТО — репорт бага "уведомление об ошибке публикации не по центру" (НЕ ЗАВЕРШЕНО, кода не менялось)

Пользователь сообщил: уведомление об ошибке загрузки сборки на GitHub (`Admin.PublishError.
MessageBox` в `AdminWindow.PublishButton_Click`, строка с `MessageBox.Show(this, ...)`) всплывает
не по центру активного окна лаунчера.

**Проверено — в текущем коде (на момент `engine-v1.19.0`) этот конкретный вызов уже передаёт
явного владельца `this`** (пофикшено в `engine-v1.17.0` вместе со всеми остальными
`MessageBox.Show` в приложении — см. блок `engine-v1.17.0` ниже). Живым прогоном в сессии
`v1.17.0` центрирование было подтверждено на другом диалоге (`PublishNoVersion`) тем же
механизмом — технически должно работать одинаково и для `PublishError`.

Спросил пользователя, на какой версии exe воспроизвёлся баг (заголовок окна клиента
"VanillaLauncher X.Y.Z" или тег релиза на GitHub, откуда скачивали) — **самая вероятная причина:
у пользователя на машине ещё старый exe, собранный ДО `engine-v1.17.0`**, и баг уже не
воспроизведётся после самообновления лаунчера (кнопка "Проверить обновление лаунчера" в
MainWindow) или скачивания свежего exe из Releases. Пользователь прервал вопрос ("жду
уточнения") — ответа на момент записи этого файла нет.

**Что делать в следующей сессии:** первым делом спроси, ответил ли пользователь на вопрос о
версии exe (или спроси заново, если это новая сессия). Если версия ≥ `engine-v1.17.0` и баг
подтверждён на ней — это реальная регрессия/недостающий кейс, нужно разбираться (возможно,
многомониторный DPI-scaling — WPF/Win32 `MessageBox` с owner иногда некорректно центрируется на
мониторах с разным DPI-масштабом; попроси скриншот с расположением обоих окон и/или проверь,
воспроизводится ли на многомониторной конфигурации). Если версия старая — просто объясни, что
нужно обновиться, баг уже закрыт.

## Последнее — редактируемый адрес сервера синхронизирован с server.properties (ОПУБЛИКОВАНО, `engine-v1.19.0`)

Прямое продолжение `engine-v1.18.0` — пользователь уточнил: в его деплоях `server-ip` в
`server.properties` обычно уже содержит Tailscale IP (сервер намеренно слушает только на этом
интерфейсе), настроено часто ДО открытия лаунчера — раньше приходилось вручную дублировать в
`AppConfig.ServerHost`. Спросил, не избыточна ли синхронизация — объяснил, что полноценный live
two-way биндинг избыточен (нужна слежка за внешними правками файла), предложил паттерн проще:
**чтение — приоритет файлу, запись — в оба места**. Пользователь согласился, реализовано.

- `ServerPropertiesReader` — новые `GetServerIp`/`GetServerPort`/`SetServerAddress` (точечная
  правка файла, порядок/комментарии не трогаются). `GetLevelName` заодно рефакторен на общий
  `GetValue` вместо дублирования построчного сканирования.
- `AdminWindow` — поля адреса стали редактируемыми (`ServerHostInlineTextBox`/
  `ServerPortInlineTextBox`). Чтение при открытии/после смены папки сервера/после "Настроек" —
  приоритет `server.properties`, фоллбек `AppConfig`. Запись по кнопке "Сохранить" — в оба
  места. Подсказка предупреждает: вступает в силу после следующего перезапуска сервера.

Пользователь **параллельно попросил обзор архитектуры** на дублирование/избыточность/
бесполезность (отдельный от этой фичи запрос) — сделан general-purpose агентом + ручная
перепроверка находок. Найдено и удалено 2 неиспользуемых ключа локализации
(`Admin.ServerStopped.MessageBox`, `Common.AppTitle`). Найдена, но НЕ тронута по решению
пользователя ("удалить только мёртвый код сейчас") копипаста между `MainWindow`/`AdminWindow`:
`SetStatus`-подобные методы (4 почти идентичные копии), тумблер языка, `Log()`, XAML-шаблон
`ListBox`-строк повторён 4 раза. Если пользователь вернётся к этой теме — рефакторинг этой
копипасты не требует функциональных решений, чисто механическая уборка.

Полная сводка — `CHANGELOG.md`/`docs/ARCHITECTURE.md`, запись `engine-v1.19.0`. 184 теста (было
175, +9). Живой прогон (PowerShell UI Automation): поля показывают значение из
`server.properties`, а не устаревшее из `appsettings.json` (проверено на специально
расходящихся тестовых значениях); после правки+сохранения — оба файла обновлены, остальные

## Ранее — диалоги центрируются на активном окне (ОПУБЛИКОВАНО, `engine-v1.17.0`)

Пользователь после `v1.16.0` попросил убрать ВСЕ всплывающие окна в боковую панель "по образцу
Итогов". При разборе выяснилось: 4 из 12 диалогов в `AdminWindow`/`MainWindow` — это
`YesNo`-подтверждения перед необратимыми действиями (пересоздание мира, публичная публикация,
закрытие при запущенном сервере, самообновление лаунчера) — их нельзя пассивно "залогировать"
без потери самого подтверждения. **Пользователь сам отменил перенос в панель** после этого
объяснения и попросил вместо этого — просто центрировать диалоги на активном окне (Client/Admin),
а не на случайном месте экрана.

Все 12 `MessageBox.Show` (10 в `AdminWindow.xaml.cs`, 1 в `MainWindow.xaml.cs`, краш-диалог в
`App.xaml.cs`) теперь передают явного владельца (`this` в окнах; в `App` —
`Windows.OfType<Window>().FirstOrDefault(w => w.IsActive) ?? MainWindow`). Причина бага: без
явного владельца WPF не гарантированно центрирует диалог на конкретном окне — заметно на
многомониторных настройках, где `AdminWindow` открыт на другом мониторе относительно исходного
`MainWindow`.

Живой прогон (PowerShell UI Automation, `GetWindowRect`): диалог теперь подтверждён как дочерний
элемент вызвавшего его окна, центр диалога практически совпадает с центром окна-владельца.
Тестов не добавлено — чисто WPF-разметка, вне зоны покрытия юнит-тестов (175 тестов без
изменений).

**Опубликовано** в этой же сессии — коммит, тег `engine-v1.17.0`, CI прошёл успешно,
`VanillaLauncher.exe` в Releases.

## Ранее — индикатор запуска сервера (ОПУБЛИКОВАНО, `engine-v1.15.0`)

Пользователь спросил про "% выполнения старта сервера" — исследовательский вопрос, ответил
кратко (точный % ненадёжен — нет единого сигнала прогресса ни в одном форке/лоадере), выбран
indeterminate-вариант.

`ServerProcessController.Started` (новое событие, срабатывает сразу после `process.Start()`,
не после готовности) + `StartupProgressBar` (новый `ProgressBar` в `AdminWindow`,
`IsIndeterminate="True"`) — показывается по `Started`, скрывается по строке `Done (...)!` или
по `Exited`. Работает одинаково для ручного "Запустить сервер" и для автоматического старта
внутри `ServerSmokeTestRunner` при публикации — оба пути идут через один и тот же `Start()`.

Один нюанс живого прогона: `timeout`/`pause` в тестовом `.bat` отказываются работать при
перенаправленном stdin (которым пользуется `ServerProcessController`) — для имитации задержки
перед `Done` использован `ping -n 4 127.0.0.1 > nul`, не `timeout /t`.

## Ранее — Forge называет виновный мод + фикс обрезания консоли (ОПУБЛИКОВАНО, `engine-v1.14.0`)

Прямое продолжение `engine-v1.13.0` — по итогам живого прогона `v1.13.0` смоук-тест сразу
поймал ВТОРОЙ инцидент на том же модпаке (`Dwarfs`) в этой же сессии: мод `VoidFog`
(`VoidFog-1.20.1-2.0.23.jar`) уронил старт (`Attempted to load class ...FogRenderer$FogMode for
invalid dist DEDICATED_SERVER`). Пользователь по скриншотам дал два фидбека: (1) панель "Ошибки"
уже содержит строку от самого Forge, которая прямо называет виновника (таблица со статусом
`ERROR`) — её нужно доставать автоматически в сообщение об ошибке, а не заставлять админа искать
глазами; (2) баг — текст в самом низу консоли обрезался по вертикали.

1. **`ForgeModStateTableParser.cs`** (новый класс, `VanillaLauncher.Admin`) — разбирает `|`-таблицу
   отчёта Forge/NeoForge о загрузке модов, ищет строки со статусом `ERROR`. Надёжнее и
   универсальнее `JarDataDescriptorScanner` (`v1.13.0`), но появляется позже (только если сервер
   пережил сканирование `mods`) — обе проверки в `PublishPipeline` идут параллельно, не
   взаимоисключающе.
2. **Фикс обрезания текста.** `VirtualizingPanel.ScrollUnit="Item"` на `LogList`/`ErrorLogList`
   (`AdminWindow`) и `LogList` (`MainWindow`) — WPF по умолчанию скроллит списки с элементами
   переменной высоты попиксельно, отсюда обрезание последней строки у нижней границы.

Полная сводка — `CHANGELOG.md`/`docs/ARCHITECTURE.md`, запись `engine-v1.14.0`. 169 тестов (было
162, +7). Живой прогон (PowerShell UI Automation на реальном exe, синтетический `.bat` с
настоящей строкой из инцидента): итоговый `MessageBox` дословно называет
`VoidFog-1.20.1-2.0.23.jar` и советует добавить в `ServerExcludeMods`; скриншот подтвердил —
последняя строка консоли/панели "Ошибки" больше не обрезается.

**Важно про параллельный живой лаунчер на машине пользователя.** Во время живого прогона в этой
сессии на экране одновременно было ДВА процесса `VanillaLauncher.exe` — мой тестовый (запущен из

поиск окон через UI Automation ОБЯЗАТЕЛЬНО фильтровать по PID своего тестового процесса
(`ProcessIdProperty`), а не только по имени окна — иначе легко случайно кликнуть в окно
пользователя вместо своего тестового.

**Опубликовано** в этой же сессии — коммит, тег `engine-v1.14.0`, CI прошёл успешно,

## Ранее — виновный jar при смоук-тесте + файловое логирование (ОПУБЛИКОВАНО, `engine-v1.13.0`)

Прямое продолжение `engine-v1.12.0` — смоук-тест сразу поймал живой инцидент на реальном
модпаке (`Dwarfs`, `D:\Modding\Servers\Servers Forge\Dwarfs`, лаунчер —
`D:\Modding\Servers\Servers Forge\Dwarfs_launcher`): три клиентских мода (`oculus`,
`smoothswapping`, `sodiumextras`) просочились на сервер, `ZipException: only DEFLATED entries
can have EXT descriptor` ронял старт, но стектрейс не называл виновный файл. Пользователь
попросил (1) научить лаунчер называть виновника автоматически и (2) добавить файловое
логирование, которого не было вообще.

1. **`JarDataDescriptorScanner.cs`** (новый класс, `VanillaLauncher.Admin`) — точный (не
   эвристика) разбор ZIP Central Directory на конкретную аномалию (STORED-запись + флаг data
   descriptor), которая крашит Forge/NeoForge при сканировании `mods`. `PublishPipeline`
   вызывает его при любом провале смоук-теста и подставляет файлы-кандидаты в сообщение об
   ошибке.
2. **`FileLogger.cs`** (новый класс, `VanillaLauncher.Client`) — один файл на запуск процесса
   (`logs/launcher-{timestamp}.log`), общий на весь процесс (`App.Logger`), пишут оба окна
   (`[Client]`/`[Admin]` префиксы) и необработанные исключения (полный `ToString()`). Чистка
   старых файлов (не больше 20) — тот же принцип, что у `WorldBackupService.MaxBackupsToKeep`.

**Живой инцидент на `Dwarfs` устранён вручную В ЭТОЙ СЕССИИ, ВНЕ этого репозитория** — на
машине пользователя, не через git: `ServerExcludeMods` в
`D:\Modding\Servers\Servers Forge\Dwarfs_launcher\appsettings.json` пополнен тремя именами
файлов, сами jar удалены из `D:\Modding\Servers\Servers Forge\Dwarfs\mods`. Это не отслеживается
никаким git-репозиторием движка/модпака. Про `VoidFog` (второй инцидент, найденный этим же
смоук-тестом сразу после публикации `v1.13.0`) — пользователь явно попросил САМ разобраться,
руками ничего не менялось.

**Опубликовано** в этой же сессии — коммит, тег `engine-v1.13.0`, CI прошёл успешно,
`VanillaLauncher.exe` в Releases.

## Ранее — смоук-тест сервера перед публикацией (ОПУБЛИКОВАНО, `engine-v1.12.0`)

По запросу пользователя, реакция на реальный инцидент: клиентский мод просочился в серверную
сборку и уронил старт сервера — обнаружилось это только постфактум, вручную, уже после того,
как обновление опубликовалось на GitHub и его скачали игроки. Пользователь явно уточнил, что
это должно решаться на стороне лаунчера/публикации, а не руками игроков.

`ServerSmokeTestRunner.cs` (новый класс, `VanillaLauncher.Admin`) — новый шаг 4/5 в
`PublishPipeline`, между синхронизацией серверных файлов и генерацией манифеста: коротко
запускает только что синхронизированный сервер, ждёт `Done (...)!`/краш/таймаут. Если сервер
не поднялся — публикация прерывается ДО загрузки чего-либо на GitHub (`ReleasePublisher` не
вызывается вообще), синхронизированные файлы сервера остаются как есть для ручного разбора.
Заодно вынесена в переиспользуемый `ServerLogLineClassifier.cs` логика
`IsSuccessLine`/`IsErrorLine`, раньше жившая только приватно в `AdminWindow` — теперь общая
между `AdminWindow` и `ServerSmokeTestRunner`. Плюс фикс гонки: смоук-тест использует тот же
`ServerProcessController`, что и кнопки "Старт"/"Стоп" в UI — без защиты `Exited`-обработчик
перетирал бы статус публикации и включал кнопки раньше времени (см. `PublishButton.IsEnabled`
как признак "публикация идёт" в `AdminWindow.EnsureController()`).

**Опубликовано** в этой же сессии — коммит, тег `engine-v1.12.0`, CI прошёл успешно,

## Как проверялась работа в прошлых сессиях (нет своего CLI-тула, только это)

Для живого прогона (сборка + запуск + клики + скриншоты) использовался PowerShell +
`System.Windows.Automation` + `System.Drawing` (скриншот окна по hwnd через
`GetWindowRect`/`Graphics.CopyFromScreen`). Рабочие скрипты этой сессии — временные, не в
репозитории, пересобирались заново по описанию:
`Add-Type -AssemblyName UIAutomationClient, UIAutomationTypes` + `Find-ByName`/
`Find-ByAutomationId`/`Invoke-Element` (`InvokePattern`)/`Select-RadioElement`
(`SelectionItemPattern`)/`Get-TextBoxValue` (`ValuePattern`). Важные нюансы:
- **Окна, открытые с `Owner = this`, оказываются в дереве UI Automation детьми
  окна-владельца, а не корня рабочего стола** — `AutomationElement.RootElement.FindFirst`
  их не находит; искать нужно и как ребёнка окна-владельца, и (fallback) как ребёнка
  root — см. `GuideWindow`/`SettingsWindow`, открытые с `Owner`. `AdminWindow` открывается
  без `Owner` (`new AdminWindow(_config).Show()`), поэтому оно — прямой ребёнок root.
- **`PasswordBox` блокирует `ValuePattern`** — пароль вводится через `SetFocus()` +
  `System.Windows.Forms.SendKeys::SendWait(...)`, не через `ValuePattern.SetValue`.
- **Скрипты обязательно сохранять как UTF-8 с BOM** (`New-Object System.Text.UTF8Encoding($true)`
  + `[System.IO.File]::WriteAllText`) — без BOM `powershell.exe` (Windows PowerShell 5.1,
  не `pwsh`) читает кириллицу как ANSI и падает с ошибками парсера на русских строковых
  литералах.
- **Копировать в рабочую папку весь `bin/Debug/net8.0-windows`, не только `.exe`** — framework-
  dependent сборка без остальных `.dll`/`.deps.json`/`.runtimeconfig.json` падает сразу при
  старте с "The application to execute does not exist: ...VanillaLauncher.dll".
- **`AppConfig.Language` персистится между запусками exe в одной и той же рабочей папке** —
  если тестовый скрипт переключил язык (кнопка сохраняет `_config.Save()`), следующий запуск
  из той же папки унаследует этот язык. Пересоздавай рабочую папку (`rm -rf` + свежий `cp -r`
  из `bin/Debug/net8.0-windows`) перед каждым независимым тестовым сценарием, если важно
  начинать с чистого/дефолтного состояния.
- Для диагностики XAML-исключений временно меняй `e.Exception.Message` на `e.Exception.ToString()`
  в `App.OnDispatcherUnhandledException` (см. `App.xaml.cs`) — полный стектрейс с номером
  строки/позиции почти всегда сразу указывает на причину; не забудь вернуть обратно перед
  коммитом.
- GitHub Actions runs проверяются напрямую через
  `api.github.com/repos/Pewdoloco/khanneli-local-launcher-minecraft/actions/runs`
  (без токена, публичный репозиторий).
