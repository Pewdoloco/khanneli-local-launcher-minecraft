## НЕ ОПУБЛИКОВАНО — фикс темы для новых окон, карточки в Инструкции/Настройках, доп. инструкции — `engine-v1.22.0` ждёт публикации

`engine-v1.21.0` (тёмная тема + карточки AdminWindow, см. блок ниже) опубликован в этой сессии.
Пользователь прогнал его живьём (реальный `Dwarfs_launcher`, четыре скриншота) и нашёл проблемы +
попросил продолжить — сделано и проверено, код не закоммичен (каждая публикация требует
отдельного подтверждения):

1. **Тема не подхватывалась новыми окнами** — `GuideWindow`/`SettingsWindow`, открытые ПОСЛЕ
   переключения на тёмную, оставались светлыми (скриншоты пользователя это подтвердили). Точечный
   `SetResourceReference` из `v1.21.0` чинил только окна, уже открытые в момент переключения.
   Настоящий фикс — `EventManager.RegisterClassHandler` на `Window.Loaded` в `App.OnStartup`,
   один раз для ЛЮБОГО окна приложения (см. `docs/ARCHITECTURE.md`, запись `engine-v1.22.0`).
2. **Обрезание нижней рамки консоли/ошибок при уменьшении `AdminWindow`** — `MinHeight="700"` из
   `v1.21.0` был занижен для реального контента карточек. Поднят до 920 (= дефолтная высота,
   физически не сжать до недостаточного размера), плюс `ClipToBounds="True"` в стиль `Card`.
3. **Карточки применены к `GuideWindow`/`SettingsWindow`** — по явному запросу пользователя
   ("и дизайн нужно применить в Инструкции и в Настройки"). `SettingsWindow` разбит на 5 карточек
   (Клиент/Сервер/Подключение/Публикация модпака/Инструкции).
4. **Дополнены встроенные инструкции** (`DefaultGuides.AdminFull`, сразу RU+EN) — два новых
   раздела по запросу пользователя: настройка Tailscale, частые ошибки администратора (включая
   TPS-диагностику через `spark`, гонку с `session.lock`, совет про Distant Horizons для FPS —
   всё это реальные инциденты из ЭТОЙ и прошлых сессий, обобщённые под generic-формулировки).
5. **Скроллбары и текст тёмной темы** — по второму раунду живого фидбека (ещё один скриншот
   `SettingsWindow`): `ScrollBar` не имел своего стиля вообще и рисовался системным светлым —
   это и были "белые рамки", не поля ввода. Новый плоский `Style TargetType="ScrollBar"` (только
   бегунок, без стрелок) + новые токены `ScrollBarThumbBrush`/`ScrollBarThumbHoverBrush` в обоих
   `Theme.*.xaml`. Заодно `TextColor` тёмной темы смягчён `#F2F2F3` → `#DADADC` (было "выжигает
   глаза").

Подробности — `CHANGELOG.md`/`docs/ARCHITECTURE.md`, запись `engine-v1.22.0`.
`EngineVersion.Current` уже поднят до `"1.22.0"` в коде (не закоммичено).

**Важный нюанс про инструкции для ЭТОГО конкретного деплоя (Dwarfs).** Если
`appsettings.json` пользователя уже когда-то сохранил `AdminGuideFull` на диск (даже нетронутым
дефолтом на момент сохранения) — новые разделы (Tailscale/частые ошибки) НЕ появятся в его
реальном "Инструкция" окне сами по себе: `DefaultGuides.Resolve` сравнивает сохранённый текст с
ТЕКУЩИМИ RU/EN константами движка, и если он не совпадает точь-в-точь (а он не совпадёт — я
дописал новые разделы), считает его "авторским" и показывает как есть. Если пользователь хочет
увидеть новые разделы — нужно либо удалить поля `AdminGuideFull`/`AdminGuideFullEn` из его
`appsettings.json` (вернутся к дефолту автоматически при следующей загрузке), либо он сам
допишет то же самое через «Настройки» → «Инструкции». Стоит предупредить об этом в следующей
сессии, если речь зайдёт о инструкциях.

**Проверено в этой сессии:** 186 тестов без изменений. Живой прогон (PowerShell UI Automation,
скриншоты, тема выставлена в `appsettings.json` тестовой копии заранее): `GuideWindow`/

чанки до ~2400-3000) — `simpleblockphysics` полностью пропал из разбора по модам (раньше 57.6%),
топ теперь `dangerous` 5.47% — подтвердило фикс под нагрузкой, не только на холостом ходу.

**Публикация модпака `1.0.5`** — после подтверждения стабильности пользователь попросил

## Ранее — два предложенных фикса, сделаны в этой же сессии (`engine-v1.20.0`)

Репо чистое, все коммиты запушены, последний тег — `engine-v1.19.0`. Всё, что было в этой сессии
после него — диагностика на живом продакшен-сервере пользователя (`Dwarfs`), НЕ в git.

**Цепочка событий этой сессии:**
1. Пользователь жаловался на высокий пинг при игре с того же ПК (вероятная причина —
   подключение через Tailscale-адрес вместо localhost, не через движок лаунчера) и TPS ~18.
2. Снял живой профиль через spark (сервер запускал Я сам напрямую — не через лаунчер — короткий
   PowerShell-скрипт в scratchpad, `start-server-only.ps1`/`spark-profile.ps1`; ключевой урок:
   скрипт можно безопасно завершать после старта сервера — дочерний java.exe переживает выход
   родительского процесса, проверено эмпирически). **Результат: `simpleblockphysics` — 57.6%
   времени серверного потока**, на порядок больше всех остальных модов вместе взятых — главный
   подозреваемый по лагам.
3. Пользователь отключил на клиенте 3 мода (Origins (Fabric), Medieval Origins Revival,
   simpleblockphysics) и попытался опубликовать — сервер не стартовал, публикация корректно не
   ушла на GitHub (это сработал смоук-тест `v1.12.0`, а не баг). Причина краша:
   `AbstractMethodError` в `apoli.util.PowerRestrictedCraftingRecipe` (apoli — библиотека внутри
   `Origins-*.jar`, отдельного файла нет, вложена как Fabric JarInJar-зависимость).
4. **Разобрались, что публикация синхронизирует ТОЛЬКО то состояние клиента, что было на момент
   попытки** — на сервере на тот момент реально был выключен только `simpleblockphysics`, Origins
   и Medieval Origins Revival остались активны (значит, они были выключены на клиенте ПОЗЖЕ,
   без повторной публикации). **Я вручную переименовал в `.disabled` все три мода прямо в
   `D:\Modding\Servers\Servers Forge\Dwarfs\mods`** (вне git, временная правка!) и подтвердил —
   сервер с ними стартует. **Это НЕ постоянный фикс** — следующая публикация пересинхронизирует
   с клиента и может откатить это, если на клиенте (CurseForge-сборке) все три ещё не выключены
   по-настоящему. Пользователю нужно: проверить клиентскую сборку → нажать "Опубликовать
   обновление" ещё раз, чтобы обновление реально ушло на GitHub (сейчас не ушло).

**Два предложенных, но НЕ согласованных фикса — спроси в начале следующей сессии, делать ли:**
- **`ServerLogLineClassifier.IsErrorLine` пропускает часть настоящих ошибок.** Реальная причина
  краша в п.3 (`java.util.concurrent.ExecutionException: ...AbstractMethodError...`) не
  начиналась ни с "Exception in thread", ни содержала `[ERROR]`/`/ERROR]` в этой конкретной
  строке — панель "Ошибки" её не поймала бы. Нужно расширить набор маркеров (например, строки,
  начинающиеся с `java.util.concurrent.ExecutionException:`, `Caused by:` уже ловится, но не
  первая строка обёртки).
- **Кнопка "Синхронизировать с сервером (без публикации на GitHub)"** в `AdminWindow` — сейчас
  единственный способ проверить, не сломает ли смена модов сервер, это либо реальная публикация
  (риск зря потратить время на смоук-тест + нужен GitHub-токен), либо ручная правка файлов
  (как сделал я в этой сессии). Кнопка прогоняла бы тот же sync+смоук-тест, что публикация, но
  без токена/подтверждения/загрузки на GitHub — пользователь сможет сам тестировать смену модов
  локально, не завися от меня каждый раз. Пользователь спросил "сделать оба фикса?" и не успел
  ответить (кончились токены) — спроси заново в начале следующей сессии.

Старый репорт "уведомление об ошибке публикации не по центру" (был открыт до этой цепочки
событий) можно считать закрытым/неактуальным — код `MessageBox.Show(this, ...)` уже верный с
`v1.17.0`, а реальная проблема пользователя в этой сессии оказалась не про центрирование, а про
сам факт падения публикации (см. цепочку выше).

## Ранее — диалоги центрируются на активном окне (ОПУБЛИКОВАНО, `engine-v1.17.0`)

Пользователь после `v1.16.0` попросил убрать ВСЕ всплывающие окна в боковую панель "по образцу
Итогов". При разборе выяснилось: 4 из 12 диалогов в `AdminWindow`/`MainWindow` — это
`YesNo`-подтверждения перед необратимыми действиями (пересоздание мира, публичная публикация,
закрытие при запущенном сервере, самообновление лаунчера) — их нельзя пассивно "залогировать"
без потери самого подтверждения. **Пользователь сам отменил перенос в панель** после этого
объяснения и попросил вместо этого — просто центрировать диалоги на активном окне (Client/Admin),
а не на случайном месте экрана.

Все 12 `MessageBox.Show` (10 в `AdminWindow.xaml.cs`, 1 в `MainWindow.xaml.cs`, краш-диалог в
`App.xaml.cs`) теперь передают явного владельца (`this` в окнах; в `App` —
`Windows.OfType<Window>().FirstOrDefault(w => w.IsActive) ?? MainWindow`). Причина бага: без
явного владельца WPF не гарантированно центрирует диалог на конкретном окне — заметно на
многомониторных настройках, где `AdminWindow` открыт на другом мониторе относительно исходного

## Как проверялась работа в прошлых сессиях (нет своего CLI-тула, только это)

Для живого прогона (сборка + запуск + клики + скриншоты) использовался PowerShell +
`System.Windows.Automation` + `System.Drawing` (скриншот окна по hwnd через
`GetWindowRect`/`Graphics.CopyFromScreen`). Рабочие скрипты этой сессии — временные, не в
репозитории, пересобирались заново по описанию:
`Add-Type -AssemblyName UIAutomationClient, UIAutomationTypes` + `Find-ByName`/
`Find-ByAutomationId`/`Invoke-Element` (`InvokePattern`)/`Select-RadioElement`
(`SelectionItemPattern`)/`Get-TextBoxValue` (`ValuePattern`). Важные нюансы:
- **Окна, открытые с `Owner = this`, оказываются в дереве UI Automation детьми
  окна-владельца, а не корня рабочего стола** — `AutomationElement.RootElement.FindFirst`
  их не находит; искать нужно и как ребёнка окна-владельца, и (fallback) как ребёнка
  root — см. `GuideWindow`/`SettingsWindow`, открытые с `Owner`. `AdminWindow` открывается
  без `Owner` (`new AdminWindow(_config).Show()`), поэтому оно — прямой ребёнок root.
- **`PasswordBox` блокирует `ValuePattern`** — пароль вводится через `SetFocus()` +
  `System.Windows.Forms.SendKeys::SendWait(...)`, не через `ValuePattern.SetValue`.
- **Скрипты обязательно сохранять как UTF-8 с BOM** (`New-Object System.Text.UTF8Encoding($true)`
  + `[System.IO.File]::WriteAllText`) — без BOM `powershell.exe` (Windows PowerShell 5.1,
  не `pwsh`) читает кириллицу как ANSI и падает с ошибками парсера на русских строковых
  литералах.
- **Копировать в рабочую папку весь `bin/Debug/net8.0-windows`, не только `.exe`** — framework-
  dependent сборка без остальных `.dll`/`.deps.json`/`.runtimeconfig.json` падает сразу при
  старте с "The application to execute does not exist: ...VanillaLauncher.dll".
- **`AppConfig.Language` персистится между запусками exe в одной и той же рабочей папке** —
  если тестовый скрипт переключил язык (кнопка сохраняет `_config.Save()`), следующий запуск
  из той же папки унаследует этот язык. Пересоздавай рабочую папку (`rm -rf` + свежий `cp -r`
  из `bin/Debug/net8.0-windows`) перед каждым независимым тестовым сценарием, если важно
  начинать с чистого/дефолтного состояния.
- Для диагностики XAML-исключений временно меняй `e.Exception.Message` на `e.Exception.ToString()`
  в `App.OnDispatcherUnhandledException` (см. `App.xaml.cs`) — полный стектрейс с номером
  строки/позиции почти всегда сразу указывает на причину; не забудь вернуть обратно перед
  коммитом.
- GitHub Actions runs проверяются напрямую через
  `api.github.com/repos/Pewdoloco/khanneli-local-launcher-minecraft/actions/runs`
  (без токена, публичный репозиторий).

## Важно знать перед продолжением

- **`test-pack` (github.com/Pewdoloco/test-pack) — удалён/приватный.** Если нужен живой
  прогон публикации — создать новый тестовый репозиторий (публичный, с README при
  создании — иначе 422 "Repository is empty" на первой публикации).
- **Файловая структура на машине пользователя может измениться между сессиями без
  предупреждения** — не полагаться на пути из истории чата не глядя, перепроверять `ls`/
  `Get-ChildItem` в начале работы.
